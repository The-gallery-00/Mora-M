# 출시 보안 변경과 적용 절차

## 변경 범위

- 앱의 스캔·이미지 확정 저장·원본 이미지 표시를 인증된 Spring 경로로 통일한다.
- Spring `POST /api/scan`, `POST /api/commit`, `GET /uploads/{imageName}`는 JWT와 실제 사용자 존재를 확인한다.
- 문서 저장·수정 때도 이미지 소유권을 확인한다. 다른 사람의 이미지 URL을 내 문서에 넣어 우회할 수 없다.
- 이미지 응답은 `private, no-store`이며 앱은 사용자별 메모리 캐시만 사용한다. 외부 URL에는 JWT를 보내지 않는다.
- OCR의 업로드·이미지 조회·삭제는 서버 간 전용 인증을 요구한다. 공개 `/`와 `/health`는 유지한다.
- 서버 간 JWT는 별도 비밀정보에서 파생한 키로 서명하며 2분 만료, 수신 대상·발급자·작업·이미지 이름을 검증한다. 일반 사용자 JWT는 이 인증을 대체할 수 없다.
- OCR 업로드의 바이트 수·이미지 크기·실제 파일 형식을 검증한다.
- 24시간이 지난 미연결 업로드와 삭제 재시도 항목을 주기적으로 정리한다. Cloud Run이 0개로 축소되거나 요청 외 CPU를 받지 못하면 실행이 늦어질 수 있으므로 정확한 보관 기한을 보장하는 작업은 아니다. 운영에서 실행 보장이 필요하면 외부 스케줄러로 보완한다.
- 소셜 로그인 3종은 브라우저 쿠키와 DB의 일회용 상태를 대조하고, 만료·제공자 불일치·재사용을 거부한 뒤 토큰을 교환한다.

## 기존 앱과의 호환성

보안 적용 후 구버전 앱의 OCR 직접 커밋과 원본 이미지 직접 조회는 거부된다.
따라서 이번 변경은 서버만 배포해서 완료할 수 없다. 수정된 앱 APK/AAB로 함께 검증해야 한다.
기존 전체 서비스 예산 알림·Cloud Run 지출 상한 설정은 이 변경으로 수정하지 않는다.

## 운영 적용 전 준비

1. DB 백업 성공 및 복구 가능 여부를 확인한다.
2. V8·V9 마이그레이션을 비운영 DB에서 확인한다. V9는 4종 문서의 기존 이미지 참조를 가져온다.
3. 서로 다른 사용자가 동일 이미지에 연결되어 있거나, 지원하지 않는 이미지 경로·JSON이 있으면 V9가 실패하도록 설계했다. 임의로 소유자를 선택하거나 기록을 삭제하지 말고 기존 데이터를 확인한다.
4. Secret Manager에 충분히 긴 임의 값의 `mora-ocr-service-secret`을 만든다. 기존 JWT 서명 비밀정보와는 별개다. 값은 코드·명령 인자·앱 환경변수·로그에 넣지 않는다.
5. Spring과 OCR 런타임 서비스 계정에 이 비밀정보에 대한 `secretAccessor`만 부여한다.
6. 두 서비스의 `OCR_SHARED_SECRET`에 같은 고정 Secret Manager 버전을 연결한다. Spring의 기존 `JWT_SECRET`은 변경하지 않는다.
7. 기존 DB·GCS·OAuth·리디렉션 설정을 보존한다. 스크립트는 추가 설정 보존을 위해 `--update-env-vars`와 `--update-secrets`를 사용한다. 기존 프로젝트의 실제 secret 이름은 배포 전 확인한다.

운영 비밀정보 생성·권한 부여·재배포는 별도 적용 작업이다. 이 문서를 추가했다고 수행된 것은 아니다.

## 배포 순서

1. 수정된 앱을 새 APK/AAB로 빌드한다.
2. 내부 검증 환경에서 같은 비밀정보를 연결한 Spring·OCR와 새 앱을 함께 검증한다.
3. 운영 전환 시 두 서버를 함께 교체한다. Spring의 Flyway가 V8·V9를 적용한다.
4. 전환 중 혼합 리비전이 서로 다른 인증 계약을 쓰면 OCR가 실패할 수 있으므로 점검 시간을 정하고 전환한다.
5. 새 앱을 내부 테스트 트랙으로 배포해 실제 소셜 로그인·촬영·앨범·이미지 표시·삭제를 검증한다.
6. 기존 앱 사용자는 업데이트가 필요함을 알린다. 검증하지 않은 상태에서 공개 출시하지 않는다.

## 완료 판정 테스트

- 무인증 Spring/OCR 업로드와 원본 접근이 차단된다.
- A 계정 이미지는 A만 볼 수 있고 B의 조회·문서 첨부는 거부된다.
- 홈 마감 임박·보관함·검색·상세·편집·전체 이미지 화면이 새 앱에서 보인다.
- 4종 각각 촬영과 갤러리 입력으로 인식·확인·저장·조회가 된다.
- 개별 삭제, 이미지 교체, 전체 문서 삭제, 계정 탈퇴가 해당 DB·이미지를 정리한다.
- 같은 이미지를 참조하는 문서가 남아 있다면 조기 삭제하지 않는다.
- OCR 삭제 실패가 DB 문서를 조용히 지워버리지 않으며 재시도할 수 있다.
- 여러 이미지 중 일부를 지운 뒤 후속 삭제가 실패하면 DB는 롤백되지만, 이미 성공한 저장소 삭제는 되돌릴 수 없다. 재시도는 가능하되 이 부분 실패에서 원본 복구까지 보장하지 않는다.
- 새 업로드가 계정 삭제와 겹치는 경우도 확인한다.
- 소셜 로그인은 정상 흐름, 취소, 누락·불일치·만료 상태, 동시 재시도와 재사용을 확인한다.
- Cloud Run 재시작 후에도 이미지 소유권과 OAuth 상태 검증이 유지된다.

## 로컬 테스트

2026-11-04 검증 결과:

- JDK 21 + 임시 pgvector PostgreSQL에서 서버 테스트 142개 통과, 실패·오류·건너뜀 0개.
- 실제 로컬 Spring·FastAPI 경로와 DB를 연결한 통합 확인 129개 통과. OCR 추론 엔진만 고정 출력으로 대체했다.
- Python 인증·업로드·실제 라우트 테스트 12개 통과.
- 앱 이미지·토큰 전달·캐시 분리·커밋 계약 테스트 9개 통과 및 TypeScript 검사 통과.
- V1~V9 적용, 구형 JSON 이미지 참조 이전, 교차 계정 차단, 4종 문서 개별 삭제, 탈퇴, 동시 처리·삭제 재시도를 확인했다.
- 운영 GCS/IAM, 실기기 UI·카메라와 외부 소셜 제공자의 실제 로그인 완료는 미검증이다.
- 운영 배포·새 앱 빌드·원격 push는 수행하지 않았다.

Spring은 JDK 21에서 `mvn test`를 실행한다. DB 통합 테스트는 각 테스트가 명시한 환경변수로 비운영 PostgreSQL을 지정해야 한다.

```sh
npm run typecheck
node --test scripts/test-document-security.cjs
python3 -m venv /tmp/mora-security-tests
/tmp/mora-security-tests/bin/pip install -r server/ocr/requirements-test.txt
PYTHONPATH=server/ocr /tmp/mora-security-tests/bin/python -m unittest discover -s server/ocr/tests -v
```

OCR 보안 테스트는 비싼 추론 엔진을 대체한다. OCR 정확도·실기기 카메라·GCS 운영 권한·실제 제공자 로그인까지 검증한 것으로 해석하지 않는다.

## 남는 범위

- 과거에 업로드했지만 어떤 문서에도 연결되지 않은 GCS 객체는 소유자를 확정할 수 없다. 자동으로 다른 사용자에게 귀속하거나 무조건 삭제하지 않는다. 별도 보관 정책과 조사 작업이 필요하다.
- GCS soft delete와 DB 백업의 보관 기간은 실제 운영 설정대로 개인정보처리방침에 반영한다.
- 소셜 로그인 보안용 브라우저 쿠키와 해시된 상태값은 최대 10분 유효하다. 실제 쿠키 사용과 정리 시점을 개인정보 고지에도 반영한다.
- 앱 복귀 URL에 JWT를 넣는 기존 소셜 로그인 계약은 유지한다. 후속으로 짧은 일회용 코드 교환과 검증된 앱 링크를 검토한다.

JWT 검증 API 참고: [PyJWT 문서](https://pyjwt.readthedocs.io/en/stable/api.html).
