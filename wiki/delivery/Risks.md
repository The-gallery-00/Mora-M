# Risks

MORA 모바일 이식 프로젝트의 리스크 등록부. 원본 코드에서 **이미 확인된 결함**과 모바일 전환에서 **새로 생기는 위험**을 모두 담는다.

## 1. 등급 정의

| 영향도 | 의미 |
|---|---|
| **치명** | 릴리스가 불가능하거나, 사용자 데이터가 소실되거나, 제품 핵심 기능이 동작하지 않는다 |
| **높음** | 주요 기능 1개가 사용 불가하거나, 페이즈 일정이 3일 이상 밀린다 |
| **중간** | 특정 조건에서 UX가 나빠지거나, 일정이 1~2일 밀린다 |
| **낮음** | 불편하지만 우회 가능하고 일정 영향이 없다 |

| 발생가능성 | 기준 |
|---|---|
| **확실** | 이미 발생했거나, 조치 없이는 반드시 발생한다 |
| **높음** | 50% 이상 |
| **중간** | 20~50% |
| **낮음** | 20% 미만 |

**등급 = 영향도 × 발생가능성.** `치명×확실`·`치명×높음`·`높음×확실` 은 **P1**(해당 페이즈 착수 전 대응책 확정 필수), 그 외 `치명`/`높음` 조합은 **P2**(페이즈 내 처리), 나머지는 **P3**(관찰).

### 2026-08-05 갱신 — OCR 전면 장애 실측 반영 (RSK-41 재개방)

**RSK-41 을 재개방한다.** 2026-07-28 에 "Cloud Run 에서 이미 구동 중"이라는 이유로 닫았는데, 이것은 §5 규칙 3("리스크는 닫을 때 근거를 남긴다 — 검증 항목을 인용한다")을 위반한 종료였다. **"돌고 있다"는 "무게 문제가 해결되었다"의 근거가 아니다.** 그 무게가 그대로 남아 사용자 신고 "OCR 이 안 된다"로 터졌다.

| ID | 조기경보 | 완화 | 터졌을 때 |
|---|---|---|---|
| RSK-41 | 특정 크기 이상의 사진에서만 스캔이 실패한다. 응답이 **JSON 이 아니라 `text/plain` 본문의 `Service Unavailable` 503** 이다. 작은 사진은 정상이므로 "가끔 안 된다"로 보고된다 | ① `PaddleOCR(...)` 생성자에 검출·인식 모델명과 `text_det_limit_side_len=960` / `text_det_limit_type="max"` 를 **명시**한다(적용 완료) ② `paddleocr`·`paddlepaddle` 버전을 `requirements.txt` 에 고정한다 — 미고정이면 재빌드마다 기본 검출 모델과 메모리 특성이 조용히 바뀐다(적용 완료) ③ 픽셀 수 방어선을 **긴 변이 아니라 면적** 기준으로 둔다 — 긴 변 가드는 1280×1280 같은 정사각 입력을 그대로 통과시키는데, 디코드 버퍼(RGB 3바이트/px)는 긴 변이 아니라 **면적**에 비례하기 때문이다. 실제 방어선은 `HARD_MAX_PIXELS`(50Mpx, **디코드 전에 거부**)이고, `RESIZE_MAX_PIXELS`(4Mpx)는 방어선이 아니라 "여기부터 줄여서 넘긴다"는 품질/비용 노브다(적용 완료) ④ Cloud Run 메모리를 2Gi 로 명시 배포(`server/cloudrun/deploy-ocr.ps1`) | OCR 전 기능 정지. 앱 로그에는 원인이 남지 않는다 — 앱 코드가 만든 503 이 아니라 **Google Frontend 가 대신 낸 503** 이기 때문이다 |

> **2026-08-05 4차 정정 — 위 ③ 이 3차까지 적고 있던 근거는 이미 철회된 것이었다.** 종전 문장은 상수 이름을 `MAX_PIXELS` 로 쓰고 근거를 "**peak 메모리가 W×H 에 선형이라**"로 달았다. 두 가지가 모두 낡았다.
> · **이름**: 상수는 `RESIZE_MAX_PIXELS`(리사이즈 트리거) 와 `HARD_MAX_PIXELS`(진짜 상한) 둘로 갈라졌다. `MAX_PIXELS` 라는 이름 자체가 "이 위는 거부된다"는 거짓 신호라서 개명된 것이다(`server/ocr/src/ocr/paddle_ocr_engine.py`).
> · **근거**: "peak 이 W×H 에 선형" 은 **생성자 수정 전에만 성립하던 사실**이고, `paddle_ocr_engine.py` 의 `RESIZE_MAX_PIXELS` 주석이 실측으로 **명시적으로 철회**했다 — det 입력을 긴 변 960 으로 clamp 한 뒤로는 1.2Mpx~27Mpx 구간에서 peak 이 약 1.0GB 로 **평평하다**([[ADR-002 Backend Connectivity]] §0-B).
> 면적 기준이라는 **결론은 유효하다.** 다만 근거가 "추론 peak" 이 아니라 "**디코드 버퍼**" 로 바뀌었다. 이것은 말장난이 아니라 상한을 조정할 때 쓰는 식이 달라진다는 뜻이다 — 50Mpx 를 올리려는 사람은 추론 peak 이 아니라 `48Mpx PNG → 전이 peak +263MB` 라는 디코드 측 실측(같은 파일 `HARD_MAX_PIXELS` 주석)에서 외삽해야 한다.

**실측치 — 정본은 [[ADR-002 Backend Connectivity]] §0 이다. 이 문서는 숫자를 복제하지 않는다.**

요지만 옮기면 이렇다(수치·측정 조건은 링크 쪽을 볼 것):

- 생성자를 고치자 **요청당 peak 메모리가 약 7.4배 줄었다**(7GB대 → 1GB 미만). 2Gi 예산 안으로 들어왔다는 것이 이 수정의 전부다.
- **peak 은 입력 해상도에 거의 반응하지 않는다.** det 입력이 긴 변 960 으로 clamp 되어 상수 크기가 되기 때문이다.
- **소요 시간은 픽셀 수가 아니라 검출 블록 수에 선형이다.** 그래서 시간 값을 인용할 때는 반드시 **블록 수**를 함께 적어야 한다.

> **2026-08-05 4차 정정 — 이 자리에 있던 표 두 개를 지우고 링크로 바꿨다. 그 표가 만든 문제가 이번 라운드에서 잡혔다.**
>
> **문제 1 — 정본이 두 개였다.** 3차에서 [[ADR-002 Backend Connectivity]] §0 은 같은 숫자에 "블록 수·프로세스 상태 미기재 · 재측정과 대조 필요" 경고를 붙였는데, 이 문서는 같은 숫자를 경고 없이 싣고 **"이 수치가 정본이다"** 라고 선언했다. 한 프로젝트에 정본이 둘 있고 **서로 다른 말을 하는** 상태였다. 정본을 [[ADR-002 Backend Connectivity]] §0 **한 곳**으로 정한다 — 리스크 문서는 "무엇이 위험한가"를 말하는 곳이지 계측 기록을 보관하는 곳이 아니다.
>
> **문제 2 — 지운 표의 숫자 자체가 조건이 섞인 값이었다.** `소요 시간 23.20s → 1.87s` 는 개선폭이 아니라 **21블록 이미지와 4블록 이미지를 비교한 값**이었다. 같은 21블록끼리는 `23.20s → 10.66s`(약 2.2배)다. 마찬가지로 `전부 1.5~1.9s` 도 블록 수가 기재되지 않은 합성 입력의 값이라 실제 명함 스캔 시간을 대표하지 않는다. 상세는 [[ADR-002 Backend Connectivity]] §0-A2.
>
> → §5 에 규칙 8 을 추가한다: **같은 실측치를 두 문서에 복제하지 않는다. 정본 한 곳을 정하고 나머지는 링크한다.**

원인은 `server/ocr/src/ocr/paddle_ocr_engine.py` 의 `PaddleOCR(...)` 생성자에 **검출 모델과 검출 입력 상한이 지정되지 않았던 것**이다. `lang="korean"` 이 중량 `PP-OCRv5_server_det` 로 해석되고 기본 `text_det_limit_type="min"` 이 큰 입력을 축소하지 않아, 요청당 peak 메모리가 **픽셀당 약 5.1KB 로 선형** 증가했다. 약 20만 픽셀을 넘는 입력에서 인스턴스가 죽는다. 상세는 [[ADR-002 Backend Connectivity]] §0.

**정정 재정정 (2026-08-05, 같은 날 2차)** — 위 RSK-43 완화책의 인용이 한 번 더 틀렸다. 1차 정정에서 "120초(`src/services/http.ts` `UPLOAD_TIMEOUT_MS`)" 로 적었는데, **그 상수는 현재 도달 불가능한 죽은 값**이다. `request()` 안의 `formData ? UPLOAD_TIMEOUT_MS : ...` 가 유일한 독자인데 `src/`·`app/` 전체에서 `request()` 에 `formData` 를 넘기는 호출부가 0건이다. 스캔·커밋은 진행률/취소 때문에 XHR 을 직접 구성하며 `http.ts` 를 거치지 않는다. **실제 상한은 `src/features/scan/api.ts` 의 `SCAN_TIMEOUT_MS`(120초)** 다. 값은 우연히 같았지만 인용이 가리키는 파일이 틀렸고, 그건 "gunicorn `--timeout 300`" 을 지운 자리에 새 거짓을 넣은 것이다 — 아래 규칙 6 이 요구하는 것은 **파일이 존재하는지**가 아니라 **그 코드가 실제로 그 역할을 하는지**까지다.

**이 사건이 남긴 문서 규칙** — 이번 근본원인 추적이 오래 걸린 가장 큰 이유는 코드가 아니라 **문서가 존재하지 않는 인프라를 사실로 기술**하고 있었기 때문이다(`ocr/cloudbuild.yaml`, gunicorn `--timeout 300`, 빌드 중 모델 워밍, NER 가중치 844MB rsync — 전부 이 레포에 존재한 적 없음). §5 에 규칙 6 을 추가한다: **위키가 인프라를 사실로 적을 때는 레포 안에 실재하는 파일 경로를 근거로 달고, 근거 파일이 사라지면 그 서술도 함께 지운다.**

### RSK-02 — PaddleOCR 콜드스타트·추론 지연

**영향도** 높음 · **발생가능성** 높음 · **등급 P1** · **Phase 3**

**모델은 컨테이너 기동 시 로드된다. 지연 로드가 아니다.** `server/ocr/services.py` 마지막 줄의 `pipeline = BusinessCardPipeline()` 이 **모듈 임포트 시점**에 실행되고, 그 생성자가 `PaddleOCREngine()` → `PaddleOCR(...)`(`server/ocr/src/ocr/paddle_ocr_engine.py:220`)를 만든다. 이 임포트는 요청과 무관하게 프로세스 기동 중에 일어난다 — `uvicorn app:app` → `server/ocr/app.py:97 from routers import ocr` → `server/ocr/routers/ocr.py:93 from services import pipeline`.

그러므로 사용자가 겪는 "첫 스캔만 유독 느리다"의 정체는 **모델 지연 로드가 아니라 Cloud Run 콜드스타트**다. `min-instances=0` 이면 컨테이너 기동 + 모델 로드가 첫 요청 앞에 통째로 붙는다 — 실측 **18~33초**([[ADR-002 Backend Connectivity]] §0-1). 두 번째 요청부터는 이 비용이 사라지고, 남는 것은 아래 "추론 시간" 뿐이다.

> **2026-08-05 3차 정정 — 이 항목은 1·2차 정정을 통과하지 못했다.** 종전 서술은 "부팅 시 모델을 로드하지 않고 **첫 요청 때 지연 로드**한다(주석: \"Render가 포트를 빨리 열 수 있도록\")" 였다. **그런 주석은 이 레포에 없다** — `grep -rni render server/ocr/ --include=*.py` → 0건. 그리고 위에 적은 대로 로드 시점은 임포트, 즉 기동 시다. 같은 세트의 [[ADR-002 Backend Connectivity]] §0-1 은 "**런타임 첫 import 시**"로 맞게 적혀 있어 **두 문서가 서로 모순**이었고, 그중 틀린 쪽이 이 문서였다. Render 는 이 프로젝트가 쓴 적 없는 호스팅이다(§호스팅 확정은 Cloud Run). 원본 웹 레포의 주석이 옮겨 적힌 것으로 보인다(§5 규칙 6).

### RSK-03 — OAuth 콜백이 앱으로 돌아오지 않음 / 구글 임베디드 웹뷰 차단

**영향도** 치명 · **발생가능성** 높음 · **등급 P1** · **Phase 2**

원본 OAuth는 **웹 브라우저 + localStorage + `FRONTEND_URL` 리다이렉트**에 완전히 묶여 있다. `/auth/{provider}/callback` 은 JSON도 302도 아닌 **`text/html` 브리지 문서**를 반환하고, 그 안의 스크립트가 `{FRONTEND_URL}/dashboard?token=...` 으로 `window.location.replace` 한다. 앱 커스텀 스킴(`mora://`)은 어디에도 등록되어 있지 않다.

[[Phases]] Phase 2의 결정은 "인앱 WebView로 열고 네비게이션 URL을 가로챈다"이다. 이 방식의 급소는 **구글이 임베디드 웹뷰에서의 OAuth를 정책적으로 차단**한다는 점이다(`disallowed_useragent` 에러). 카카오·네이버는 통상 허용된다.

| 항목 | 내용 |
|---|---|
| 조기경보 | 구글 동의 화면 대신 "이 브라우저 또는 앱은 안전하지 않을 수 있습니다" 페이지가 뜸. 또는 콜백 후 웹뷰가 빈 화면(웹 프론트 :3000 미기동)에서 멈추고 토큰을 못 잡음 |

### RSK-06 — RN `FormData` 멀티파트 형식 차이로 업로드 실패

**영향도** 치명 · **발생가능성** 중간 · **등급 P1** · **Phase 3**

웹 `FormData` 는 `File` 객체를 넣지만 RN은 `{ uri, name, type }` 객체를 넣는다. `Content-Type` 을 수동 지정하면 boundary가 깨지고, `type` 을 빠뜨리면 Spring이 파트를 인식하지 못해 400/500이 난다. 서버는 파트명이 정확히 `"file"` 이어야 한다(`@RequestParam("file") MultipartFile`).

| 항목 | 내용 |
|---|---|
| 조기경보 | `/api/scan` 이 400 또는 500을 반환하고 서버 로그에 `Required part 'file' is not present` 또는 multipart 파싱 오류 |
| 완화 | ① **Phase 3의 첫 UoW를 "명함 1장 업로드 성공"에 배정** — 화면을 만들기 전에 통신부터 뚫는다 ② `Content-Type` 헤더를 **절대 수동 설정하지 않는다**(원본 프론트도 동일 주의) ③ 파트명 `file`, `name` 에 확장자 포함(`scan.jpg`), `type` 에 정확한 MIME(`image/jpeg`) ④ 커밋 요청의 텍스트 파트 3개(`document_type`, `raw_blocks`, `corrected_fields`)는 문자열로 append |
| 대응 | `expo-file-system` 의 `uploadAsync(url, uri, { uploadType: MULTIPART, fieldName: 'file', parameters: {...} })` 로 전환. 이 API는 네이티브 레벨에서 멀티파트를 구성하므로 RN `FormData` 이슈를 우회한다. 진행률 콜백도 함께 얻는다(FR-040에 유리) |

### RSK-07 — 포스터·영수증 파서가 사실상 미완성

**영향도** 높음 · **발생가능성** 확실 · **등급 P1** · **Phase 3**

- **영수증**: OCR이 추출하는 필드가 `store_name / purchase_date / total_amount` **3개뿐**이다. `merchantAddress / purchaseTime / paymentMethod / cardCompany / currencyCode` 는 스키마에만 있고 OCR이 채우지 않는다. 품목(`items`)은 `_build_receipt_items` 함수 자체가 존재하지 않아 **항상 `[]`** 다.
- **포스터**: `fee`(참가비)와 `description`(설명)이 OCR 스키마·ML 라벨 어디에도 없어 **항상 빈 문자열**이다. 날짜에 연도가 없으면 **올해로 가정**한다(연말/연초 오답).
- 필드 추출 모델 메타의 자기 경고: "real_eval labels are rule-based weak labels (upper bound = rule performance). True real-world F1 requires gold correction." → 실제 성능은 검증된 바 없다. NER 학습 데이터는 **총 6건**(명함 2, 포스터 4)뿐이다.

| 항목 | 내용 |
|---|---|
| 조기경보 | 영수증 스캔 결과 폼에 값이 1~2개만 채워짐. 포스터 참가비/설명이 항상 공백 |
| 완화 | ① **필드 편집 UI를 "선택 기능"이 아니라 필수 단계로 설계**한다 — 자동 추출만으로 저장이 완결된다는 전제를 두지 않는다 ② 빈 필드를 회색 placeholder로 명확히 보여주고 "확인 후 저장" 문구를 넣는다 ③ 영수증은 3필드만 폼 상단에 두고 나머지는 "추가 정보(선택)" 섹션으로 접어 둔다 ④ 포스터 날짜는 연도가 추론된 경우 연도 부분을 강조해 사용자 확인을 유도 |
| 대응 | 정확도 개선은 **모바일 프로젝트 범위 밖**이다([[Scope]]). 앱은 "사람이 고치기 쉬운 폼"을 제공하는 것으로 대응하고, 개선 요청은 OCR 팀 백로그로 넘긴다. 사용자가 고친 값은 `/api/commit` 의 `corrected_fields` 로 NER 데이터셋에 축적되므로, **앱이 잘 쓰일수록 학습 데이터가 쌓이는 구조**임을 이해관계자에게 설명한다 |

### RSK-08 — 업로드 1회에 서버 이미지가 3개 생성됨

**영향도** 높음 · **발생가능성** 확실 · **등급 P1** · **Phase 3**

기존 프로젝트의 미해결 이슈로 보고된 항목이다: "1회 업로드에 TYPE 폴더에 파일 3개 생성됨, 원인 미확인." 모바일에서도 재현되면 디스크가 3배로 차고 `.hash_index.json` 중복 기록이 쌓인다(해시 인덱스는 **기록만 하고 중복을 차단하지 않는다**).

| 항목 | 내용 |
|---|---|
| 조기경보 | `ocr/uploads/{TYPE}/` 의 파일 수가 저장 횟수의 배수로 증가. `.hash_index.json` 에 동일 MD5가 여러 항목 |
| 완화 | ① **QA-047을 Phase 3 DoD에 포함** — 저장 1회 후 파일 증가가 정확히 1개인지 매번 확인한다 ② 앱 쪽 원인 후보(저장 버튼 중복 탭, React 이펙트 중복 실행, 재시도 로직)를 먼저 제거: 저장 버튼에 in-flight 가드, 커밋 요청에 멱등 키 역할을 하는 요청 ID 로깅 ③ 앱은 커밋을 **정확히 1회만** 호출하고, 실패 시 자동 재시도하지 않는다(사용자 명시 재시도만) |
| 대응 | 앱에서 1회만 호출하는데도 3개가 생기면 원인은 서버(OCR `_persist_image`)에 있다 → 백엔드 무수정 원칙의 **예외 사유**로 등록하고 OCR 담당(김민우)에게 이관. 그때까지는 "저장 1회 = 파일 3개"를 알려진 제약으로 릴리스 노트에 명시 |
| 근거 | 이 결함은 이번 정찰(`scout/*`)에서 재확인되지 않았다. 즉 **원인이 앱 쪽일 수도, 서버 쪽일 수도 있는 미확정 상태**다. 그래서 완화책을 양쪽에 걸었다 |

### RSK-11 — Spring multipart 10MB 한도와 규격 밖 에러 응답

**영향도** 높음 · **발생가능성** 높음 · **등급 P1** · **Phase 3**

`spring.servlet.multipart.max-file-size: 10MB`. 폰 원본 사진은 4~12MB다. 초과하면 `MaxUploadSizeExceededException` 이 발생하는데, 이 프로젝트에는 **`@ControllerAdvice` 전역 예외 핸들러가 없다**. 따라서 `{"success":false,"error":...}` 가 아니라 **Spring 기본 에러 JSON**(`{"timestamp":...,"status":...,"error":"...","path":"..."}`)이 내려온다. `json.success` 를 전제로 한 앱 파서는 여기서 깨진다.

| 항목 | 내용 |
|---|---|
| 조기경보 | 큰 사진에서만 스캔 실패. 응답 본문에 `timestamp`/`path` 키가 보임 |
| 완화 | ① 업로드 전 **전송 장변 1280px / JPEG q0.85 압축**(FR-039) → 통상 300KB~1.2MB ② 목표 1.2MB 초과 시 재압축 사다리(q0.85→0.70→…)로 하향, 하드 상한 8MB([[Camera and Scan]] IMG-01~07) ③ 공통 응답 파서를 `success` 부재에 내성 있게 작성: `json?.success === false ? json.error : (json?.error ?? json?.message ?? \`요청 실패 (${status})\`)` ④ ABN-28로 회귀 검증 |
| 대응 | 압축 실패 시 사용자에게 "이미지가 너무 큽니다. 다시 촬영해 주세요" 안내. 서버 한도 상향은 백엔드 수정이므로 v1 범위 밖 |

### RSK-12 — 평문 HTTP 차단과 cleartext 보안 부채

**영향도** 치명 · **발생가능성** 확실 · **등급 P1** · **Phase 0, 8**

백엔드가 `http://<LAN_IP>:8080`, `http://<LAN_IP>:8000` 평문이다. Android 9(API 28)부터 `cleartextTrafficPermitted` 기본값이 false이므로 **설정 없이는 APK에서 모든 API가 즉시 실패**한다. 그리고 이걸 허용하면 릴리스 APK가 모든 도메인에 평문 통신을 허용하는 상태가 된다.

| 항목 | 내용 |
|---|---|
| 조기경보 | Expo Go/개발 빌드에서는 되는데 APK에서만 전 API가 `Network request failed` |

### RSK-16 — `/api/commit` 실패 무시로 인한 고아 데이터

### RSK-17 — 응답 이중 래핑 + snake/camel 혼재

**영향도** 높음 · **발생가능성** 높음 · **등급 P2** · **Phase 3**

### RSK-18 — 문서 id 타입 불일치

**영향도** 중간 · **발생가능성** 높음 · **등급 P2** · **Phase 4**

|---|---|

| 완화 | ① 앱 모델에서 `id` 를 **`string` 으로 통일해 다루되**, 요청 URL을 만들 때 유형별로 그대로 문자열 삽입한다(숫자 변환·UUID 파싱을 하지 않는다 — 원본 프론트와 동일 전략) ② 문서 유형과 id를 함께 들고 다니는 `DocumentRef = { type, id }` 타입을 만들어 유형 없이 id만 넘기는 코드를 막는다 ③ ABN-27로 회귀 검증 |
| 대응 | 실패 시 어느 유형인지 즉시 드러나므로 매핑 수정으로 해결 |

### RSK-22 — 티켓 오분류 / `ETC` 저장 불가

**영향도** 중간 · **발생가능성** 높음 · **등급 P2** · **Phase 3**

이미지 분류 모델의 클래스는 **3개**(`namecard`, `poster`, `recipt`)뿐이고 **티켓 클래스가 없다.** 티켓은 OCR 텍스트에 `TICKET_KEYWORDS` 중 **2개 이상**이 매칭되면 확정되며 이때 `confidence = 1.0` 을 **하드코딩**한다(실제 신뢰도가 아니다). 반대로 명함·포스터에 "도착"·"좌석" 같은 단어가 우연히 둘 있으면 티켓으로 오분류된다. `CONFIDENCE_THRESHOLD = 0.8` 상수는 선언만 되어 있고 **어디서도 쓰이지 않아**, 무관한 사진도 3클래스 중 하나로 강제 배정된다. 그리고 `ETC` 는 저장 경로가 없어 `지원하지 않는 문서 유형입니다.` 로 거부된다.

| 항목 | 내용 |
|---|---|
| 조기경보 | 명함을 찍었는데 티켓 폼이 뜸. 신뢰도가 항상 정확히 100.0% |
| 완화 | ① **유형 수동 변경을 1급 기능으로 배치**한다 — 결과 화면 최상단에 유형 셀렉터를 두고, 접힌 메뉴에 숨기지 않는다 ② 유형 변경 시 공통 필드 값 승계(FR-044)로 재입력 부담 제거 ③ 신뢰도 100.0%는 그대로 표시하되 신뢰도를 근거로 UI를 분기하지 않는다 ④ `ETC` 는 저장 버튼 비활성 + "문서 유형을 선택해 주세요" 유도(FR-050, QA-054) |
| 대응 | 오분류는 사용자가 1탭으로 고칠 수 있으면 치명적이지 않다. 분류 정확도 개선(현재 81.2% 보고)은 OCR 팀 과제로 이관 |

### RSK-23 — 검색 호출 = 검색기록 자동 적립

**영향도** 중간 · **발생가능성** 높음 · **등급 P2** · **Phase 5**

### RSK-30 — 다크 QA 매트릭스 2배로 Phase 7 일정 초과

### RSK-31 — 하드코딩 HEX 잔존으로 다크에서 깨지는 화면

**영향도** 높음 · **발생가능성** 확실 · **등급 P1** · **Phase 1** (관찰 7)

**원본 웹이 정확히 이 실패를 이미 했다.** 페이지마다 로컬 팔레트(`const C = {...}`)를 5벌 만들고 인라인 `style`에 HEX를 직접 박았다 — CSS 변수는 정의되어 있는데도 대부분 쓰이지 않았다([[ADR-004 Styling]] 맥락). 그 코드를 참고하며 CMP 52종·화면 31개를 이식하는 동안 HEX 한 줄이 남으면, 라이트에서는 **아무 증상이 없고** 다크에서만 흰 카드·검은 글자로 드러난다. 즉 이것은 "생길 수도 있는" 위험이 아니라 **조치 없이는 반드시 발생하는** 종류이며, 그래서 P1이다. 변종도 있다: `dark:bg-black` 같은 색 분기(HEX가 아니라 grep을 통과한다), RN `useColorScheme()` 직접 호출(색을 쓰지 않지만 `시스템 따름`이 아닌 사용자에게 틀린 테마를 준다), 모듈 최상단에서 `colors`를 import해 테마 변경에 반응하지 않는 코드.

| 항목 | 내용 |
|---|---|
| 조기경보 | 다크에서 **특정 화면·특정 컴포넌트만** 흰 배경으로 남음. 테마를 바꿔도 안 바뀌는 요소가 있음. `grep -rn "#[0-9A-Fa-f]\{6\}"` 결과가 0이 아님 |
| 완화 | ① **린트/grep 게이트 4개를 커밋 게이트로 강제**([[QA Checklist]] §6-2): 하드코딩 HEX 0건 · `dark:` 색 분기 0건 · RN `useColorScheme` import 0건(ESLint `no-restricted-imports`) · `global.css` 드리프트 0 ② 색 출처를 구조적으로 하나로 묶는다 — 컴포넌트는 `className`(CSS 변수) 또는 `useTheme()`만 통과하고 `palette.*` 직접 import를 금지([[Design Tokens]] §0 규칙 3) ③ **한 테마에서만 검수된 컴포넌트 머지 금지** — PR에 두 테마 스크린샷 첨부([[ADR-004 Styling]] §5-7) ④ 갤러리 화면에 테마 토글을 두어 **그 페이즈 산출분을 한 화면에서 동시 비교**(Phase 1 = 23종, 산출 시점 검수 FR-128 · THM-10)하고, 누적 52종의 검수 완료는 Phase 7 게이트(FR-112)에서 확인 |
| 대응 | 발견 시 화면에서 색을 덧칠하지 않는다. 해당 HEX가 어떤 의미론적 토큰인지 판정해 `tokens.ts`의 토큰으로 교체하고, 대응 토큰이 없으면 **토큰을 추가**한 뒤 §10-3 표에 대비비와 함께 등재한다. 게이트를 통과했는데도 다크가 깨졌다면 원인은 HEX가 아니라 elevation·오버레이·이미지이므로 [[QA Checklist]] §2-5 실패 처리 순서를 따른다 |
| 왜 P1인가 | 이 항목만 다른 다크 리스크(RSK-29/30/32)보다 등급이 높은 이유는 **완화책이 페이즈 착수 전에 존재해야만 작동**하기 때문이다. Phase 1 코드가 이미 쌓인 뒤에 grep 게이트를 켜면 수백 건이 한꺼번에 터져 게이트를 끄게 된다. 그래서 Phase 1 **첫 커밋 전에** 게이트가 CI/스크립트로 살아 있어야 한다 |

### RSK-33 — NativeWind 4가 Tailwind 4를 지원하지 않아 버전 고정에 묶임

**영향도** 중간 · **발생가능성** 확실 · **등급 P2** · **Phase 1**

`nativewind 4.2.6` 이 선언한 peer 범위는 `tailwindcss > 3.3.0` 이다. 그래서 **Tailwind 4가 설치되는 것을 npm이 막지 않는다.** 그러나 NativeWind 4 계열은 실제로 Tailwind 4를 지원하지 않고(Tailwind 4 지원은 `nativewind@5.0.0-preview.4` 계열뿐), 4를 넣으면 설정 파일 형식(`@theme` / CSS-first config)이 어긋나 **색 토큰이 조용히 적용되지 않는다.** 다크모드가 CSS 변수 2벌에 전면 의존하는 이 프로젝트에서는 그 침묵이 곧 테마 붕괴다.

**즉 위험은 "Tailwind 4를 못 쓴다"가 아니라 "peer 범위가 넓어서 실수로 4가 들어와도 즉시 티가 나지 않는다"** 이다.

| 항목 | 내용 |
|---|---|
| 조기경보 | `npm ls tailwindcss` 가 4.x를 출력. `className` 의 색이 적용되지 않는데 오류는 없음. `tailwind.config.js` 가 무시되는 듯한 증상 |
| 완화 | ① **`tailwindcss@3.4.x` 고정**([[Tech Stack]] VR-7) — `package.json` 에 `^` 없이 명시 ② `npx expo install --check` / `expo-doctor` 를 커밋 게이트에 유지 ③ NativeWind 5 preview를 v1 기반으로 삼지 않는다 — Phase 1~7 전체가 preview 위에 쌓이면 되돌릴 수 없다 ④ Tailwind 4의 신문법(`@theme`, CSS-first config)을 **위키 예시에 쓰지 않는다** — 원본 웹이 Tailwind 4라서 그 문법을 그대로 옮기려는 유인이 실재한다 |
| 대응 | 4가 들어왔다면 `npm i -D tailwindcss@3.4` 로 되돌리고 `global.css` 를 재생성(`npm run theme:css`)한 뒤 두 테마를 눈으로 확인한다 |
| **재검토 트리거** | **`nativewind@5` 정식 릴리스.** 그때 Tailwind 4로 올릴지 판단한다. 판단 기준은 "우리가 Tailwind 4의 기능을 실제로 원하는가"이고, 현재 답은 아니다 — 우리는 클래스명 어휘와 CSS 변수만 쓴다. 즉 **이 고정은 기능 손실이 거의 없는 고정이며**, 그래서 등급이 P2에 머문다 |

### RSK-34 — eas-cli ↔ TypeScript 6 충돌로 app config가 `.js` 로 제약됨

**영향도** 중간 · **발생가능성** 확실(이미 발생) · **등급 P3** · **Phase 0, 8**

eas-cli는 빌드 전에 app config를 다시 읽고 필요하면 수정한다. 그 경로에서 `app.config.ts` 를 만나면 **프로젝트의 TypeScript로 트랜스파일**하는데, `typescript 6.0.3` 에서 `Cannot read properties of undefined (reading 'CommonJS')` 로 죽는다(TS 6의 `ModuleKind` API 변경). `npx eas-cli`(캐시된 21.1.0)는 **읽기 단계에서도** 같은 이유로 실패한다.

→ **대응 완료: `app.config.js` + JSDoc 타입 보조.** 트랜스파일 경로 자체가 사라져 문제가 발생하지 않는다.

이 대응이 남기는 부채는 두 개다: ① app config에서 **컴파일 타임 타입 검사가 약해진다**(JSDoc은 `tsc` 로 검사되지만 IDE 지원 수준이 `.ts` 보다 낮다), ② **동적 config라 eas-cli가 `projectId` 를 자동 기입할 수 없어 손으로 적어야 한다**([[APK Build]] §1-1).

| 항목 | 내용 |
|---|---|
| 조기경보 | eas-cli 실행 중 `CommonJS` 관련 TypeError. `app.config.ts` 를 되살리려는 PR |
| 완화 | ① app config는 **`.js` 로만 유지**한다. `.ts` 로 되돌리는 변경은 리뷰에서 반려 ② 이 문서의 사유를 `app.config.js` 최상단 주석에 적어 둔다(코드에 이미 반영됨) — 그러지 않으면 "왜 TS 프로젝트에 JS 설정 파일이 있나"는 질문이 반복된다 ③ 모든 eas 명령을 **`npx eas-cli@latest`** 로 적는다 ④ `projectId` 하드코딩을 "실수"가 아니라 **의도**로 문서화한다 |
| 대응 | eas-cli가 TS 6을 지원하면 `.ts` 로 되돌릴 수 있다. 단 되돌려야 할 이유가 약하다 — JSDoc으로 타입이 이미 붙어 있고, `.js` 는 트랜스파일 경로가 없어 **더 단순하다.** 되돌리기를 굳이 하지 않는 편이 낫다는 판단이라 등급은 P3 |
| 재검토 트리거 | eas-cli 릴리스 노트에 TypeScript 6 지원이 명시될 때 |

### RSK-36 — Expo SDK 57이 최신 라인이라 서드파티 검증 이력이 짧다

**영향도** 높음 · **발생가능성** 중간 · **등급 P2** · **Phase 0~8**

SDK 57 / RN 0.86 / React 19.2 / TypeScript 6은 **집필 시점의 최신 안정 라인**이다. 최신을 고른 것은 의도적이지만(SDK 업그레이드를 프로젝트 중간에 하지 않는다는 [[ADR-001 Framework]] 결정의 귀결), 그 대가로 **우리가 쓰는 서드파티가 이 조합에서 검증된 이력이 짧다.** Phase 0에서 만난 4건이 이미 그 증상이다: `babel-preset-expo` 중첩 설치, TS 6 ↔ eas-cli, MMKV v4의 API 파괴, `react-dom` peer 강제.

이 리스크의 성격은 RSK-25(버전 충돌 일반론)와 다르다. RSK-25는 "버전을 잘못 맞추면 깨진다"이고, **RSK-36은 "버전을 정확히 맞춰도 그 조합을 먼저 밟은 사람이 적어 검색으로 답이 안 나온다"** 이다. 후자는 `expo install`로 예방되지 않는다.

| 항목 | 내용 |
|---|---|
| 조기경보 | 오류 메시지를 검색해도 사례가 없거나 GitHub 이슈가 몇 주 전에 열린 상태. 라이브러리 README의 예시 코드가 우리 버전에서 동작하지 않음(MMKV v4가 정확히 이 경우) |
| 완화 | ① **패키지 문서보다 설치된 타입 정의를 신뢰한다** — `node_modules/<pkg>/**/*.d.ts` 가 그 버전의 실제 계약이다. MMKV v4의 `createMMKV`/`remove` 는 이렇게 확인했다 ② 위키의 서드파티 예시 코드에 **버전을 함께 적는다**([[Tech Stack]] §2-0) — 버전 없는 예시는 몇 달 뒤 거짓이 된다 ③ 네이티브 모듈이 걸린 변경은 **JS만 고쳐 놓고 넘어가지 않는다.** dev client 재빌드로 실기기 확인까지 한 뒤 커밋 ④ 각 페이즈에서 새 패키지를 처음 쓸 때 **최소 재현 화면 1개**로 먼저 검증한다 ⑤ `package-lock.json` 커밋 필수 — 되돌아갈 지점이 없으면 이 리스크는 치명이 된다 |
| 대응 | 특정 패키지가 SDK 57에서 끝내 동작하지 않으면 **SDK를 내리지 않고 그 패키지를 교체한다.** SDK 다운그레이드는 이미 통과한 Phase 0 전체(EAS 연결·keystore·매니페스트·번들)를 다시 검증하게 만든다. 교체 후보는 [[Tech Stack]] §4의 기각 목록에 이미 사유와 함께 남아 있다 |
| 재검토 트리거 | SDK 58 릴리스(그때 57이 "한 세대 전"이 되어 이력이 쌓인다) · 또는 같은 패키지에서 SDK 57 관련 이슈가 3건 이상 누적될 때 |

## 5. 리스크 운영 규칙

1. **페이즈 착수 회의에서 위 표의 해당 행을 소리 내어 읽는다.** P1 항목의 대응책이 문서·코드로 존재하지 않으면 착수하지 않는다.
2. **페이즈 종료 게이트에서 발생한 리스크를 등록한다.** [[Phases]] §5의 사용자 확인 항목이 하나라도 실패하면, 그 원인을 새 `RSK-##` 로 이 문서에 추가하고 등급을 매긴다.
3. **리스크는 닫을 때 근거를 남긴다.** "해결됨"이 아니라 "QA-047이 3회 연속 통과하여 RSK-08을 종료" 처럼 검증 항목을 인용한다.
4. **백엔드 무수정 원칙의 예외는 여기에 기록한다.** RSK-03(구글 콜백)과 RSK-08(이미지 3중 저장)이 현재 예외 후보다. 예외를 승인할 때는 승인자·사유·범위를 함께 적는다.
5. **새 리스크의 ID는 재사용하지 않는다.** 종료된 리스크도 행을 남기고 `종료` 표시만 붙인다.
6. **인프라를 사실로 적을 때는 레포 안에 실재하는 파일 경로를 근거로 단다.** 근거 파일이 사라지면 그 서술도 함께 지운다. (2026-08-05 추가 — RSK-41 재개방의 교훈. 근거 없는 인프라 서술이 OCR 장애의 근본원인 추적을 지연시켰다.)
7. **코드 상수를 인용할 때는 그 상수에 도달하는 호출부까지 확인한다.** 파일에 존재한다는 것과 실행된다는 것은 다르다. 규칙 6 을 지키고도 죽은 상수를 정본으로 인용해 같은 실수를 반복했다(RSK-43 의 `UPLOAD_TIMEOUT_MS` → `SCAN_TIMEOUT_MS` 재정정). (2026-08-05 추가)
8. **같은 실측치를 두 문서에 복제하지 않는다.** 정본 한 곳을 정하고 나머지는 링크한다. 복제본은 반드시 갈라진다 — 3차에서 [[ADR-002 Backend Connectivity]] §0 이 "조건 미기재 · 대조 필요" 경고를 붙이는 동안 이 문서는 같은 숫자를 경고 없이 "정본"으로 선언했고, 결과적으로 **정본이 둘이고 서로 다른 말을 하는** 상태가 됐다. OCR 실측치의 정본은 [[ADR-002 Backend Connectivity]] §0 이다. (2026-08-05 4차 추가)
9. **실측치에는 측정 조건을 함께 적는다.** 최소한 `입력 해상도 + 검출 블록 수 + 프로세스 상태(콜드/웜)` 셋이다. 조건을 뗀 채 옮겨 적었기 때문에 같은 입력의 소요 시간이 문서 3곳에서 `1.87s` · `10.66s` · `1.5~1.9s` 로 갈렸고, 그중 하나는 **아예 다른 이미지의 값**이었다. (2026-08-05 4차 추가)
