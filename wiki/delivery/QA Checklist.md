## 0. 사용 규칙

| 규칙 | 내용 |
|---|---|
| ID 체계 | 기능 시나리오 `QA-###` · 기기 `DEV-##` · **테마 `THM-##`** · 회귀 `REG-##` · 비정상 경로 `ABN-##` · 성능 `PERF-##` |
| 발번 규칙 | `QA-###` 는 페이즈 순서로 대역이 배정되어 있고 **대역이 꽉 차 있다.** 신규 케이스는 대역 중간에 끼워 넣지 않고 **최대 번호 뒤에 이어 붙인다**(현재 최대 **QA-210** — QA-208~210은 2026-07-27 매니페스트 권한 검증으로 신설). [[Requirements]] 의 FR 발번 규칙과 동일하며, 번호는 폐기해도 재사용하지 않는다. |
| 실행 환경 | **에뮬레이터가 아니라 실기기**. 카메라·권한·메모리·설치 흐름이 에뮬레이터에서 재현되지 않는다. |
| 테마 축 | 다크모드는 v1 In scope다([[ADR-004 Styling]] §4). **모든 화면 케이스는 암묵적으로 라이트 기준**이고, 다크에서 반복해야 하는 대상은 §2-4 의 P1 목록으로 한정한다. 테마 전환 자체의 케이스는 `THM-##`. |
| 빌드 종류 | 페이즈 중간 검증은 `development`, 페이즈 종료 게이트는 반드시 **`preview` APK**(release 서명·번들 포함) |
| 판정 | 기대결과와 **한 글자라도 다르면 실패**다. "대충 비슷함"은 통과가 아니다. |

| 실패 기록 | 실패 항목은 즉시 [[Risks]]에 등록하거나 이슈로 전환한다. 통과 표시만 남기고 넘어가지 않는다. |

## 1. 페이즈별 수동 테스트 시나리오

### Phase 0 — 기반 셋업 & APK 파이프라인 관통

| ID | 단계 | 기대결과 |
|---|---|---|
| QA-001 | `npx eas-cli@latest build -p android --profile preview` 실행 후 완료까지 대기 | 빌드 상태 `finished`, 다운로드 가능한 `.apk` URL 발급 |
| QA-002 | 발급된 APK를 실기기에 설치 (**adb가 없으므로 EAS 빌드 페이지 QR → 브라우저 다운로드** 경로) | 홈 화면에 `MORA` 아이콘 생성, 실행 시 크래시 없이 첫 화면 표시 |

#### Phase 0 추가 — 매니페스트 권한 검증 (실측으로 신설)

**왜 필요한가** — 요청하지 않은 권한 2개(`RECORD_AUDIO`, `SYSTEM_ALERT_WINDOW`)가 플러그인 병합으로 자동 유입되는 것이 확인되었다([[APK Build]] §2-1). `blockedPermissions` 가 실제로 최종 매니페스트에서 그것들을 빼는지는 **눈으로 확인해야만 알 수 있다** — 설정을 적어 두는 것과 병합 결과가 다를 수 있기 때문이다. 설치 화면에 마이크·오버레이 권한이 뜨는 앱은 사용자 신뢰를 즉시 잃는다.

| ID | 단계 | 기대결과 |
|---|---|---|
| QA-208 | `npx expo prebuild --platform android --clean` 후 `android/app/src/main/AndroidManifest.xml` 을 열어 `uses-permission` 전량 확인 (또는 설치된 APK의 앱 정보 > 권한) | **정확히 6개**: `INTERNET`, `ACCESS_NETWORK_STATE`, `CAMERA`, `READ_MEDIA_IMAGES`, `POST_NOTIFICATIONS`, `VIBRATE`. 여기에 `READ/WRITE_EXTERNAL_STORAGE` 가 **`maxSdkVersion="32"` 와 함께** 있는 것은 정상(expo-image-picker 레거시 호환). **`RECORD_AUDIO` 가 있으면 실패** |
| QA-209 | `preview` 와 `production` 매니페스트에서 `SYSTEM_ALERT_WINDOW` 검색. 이어서 `development` 매니페스트에서 같은 검색 | preview·production에는 **없고**, development에는 **있다**. 둘 다 없으면 개발 메뉴가 동작하지 않고, 둘 다 있으면 사용자에게 "다른 앱 위에 표시" 권한을 요구하는 앱이 된다 |
| QA-210 | 같은 매니페스트에서 `usesCleartextTraffic`(`android:usesCleartextTraffic`) · `package` · `minSdkVersion` · `mora` scheme intent-filter 확인 | 순서대로 `true`(preview) / `com.mora.app` / `26` / `<data android:scheme="mora"/>` 존재. **production 매니페스트에서는 cleartext가 `false`** ([[Networking]] §2-1, [[Auth]] §7-3) |

> 이 3건은 **`production` APK를 만들기 전에** 통과해야 한다. 릴리스 후에 발견하면 재빌드·재배포가 필요하고, 사이드로드 배포에서는 테스터 전원에게 다시 링크를 보내는 일이 된다.

#### Phase 0 추가 — 서버 연결·진단 (FR-121 · FR-122 · SCR-31)

**왜 이 표가 따로 있는가** — Phase 0의 P1 리스크 3건([[Risks]] RSK-01 IP 변동 · RSK-12 cleartext · RSK-24 데모 직전 전면 실패)의 **유일한 대응 수단이 SCR-31 진단 화면 하나**다. 이 화면이 "실패했다"가 아니라 **"어디가 실패했는지"** 를 지목하지 못하면 세 리스크의 완화책은 문서상으로만 존재한다. 그래서 정상 경로(QA-003·QA-004)보다 실패 경로를 더 촘촘히 나눈다. 화면 스펙은 [[Screen Specs]] SCR-31, 문구는 그 표의 **정확한 문구** 열이 정본이다.

| ID | 단계 | 기대결과 |
|---|---|---|
| QA-190 | 진단 화면에서 API base를 존재하지 않는 호스트(`http://192.168.0.99:8080`)로 바꾸고 blur → `연결 테스트` | 스킴이 정상이므로 값은 저장됨. API 행이 3초 안에 `✗ 백엔드 서버에 연결할 수 없습니다.` 로 확정. 입력값 유지, 크래시 0, 무한 스피너 없음 |
| QA-191 | 스킴 없이 `192.168.0.10:8080` 입력 후 blur | 입력칸 보더 danger + `http:// 또는 https:// 로 시작하는 주소를 입력해 주세요.` **저장되지 않고 이전 값이 유지된다** (오타 하나로 앱이 서버를 영구히 잃지 않는다) |
| QA-192 | Spring·OCR **둘 다** 중지 후 `연결 테스트` | 두 행 모두 `✗` + 각기 다른 사유 문구. 두 프로브가 병렬이므로 6초가 아니라 **3초 안에** 결과 확정. 버튼 스피너 해제됨 |
| QA-193 | 서버는 기동 상태로 두고 PC 방화벽에서 **8000 인바운드만 차단** → `연결 테스트` | OCR 행 `✗ OCR 서버(:8000)에 닿지 않습니다. 방화벽 8000 포트를 확인하세요.` — "서버 미기동"과 **구분되는 문구**가 나와야 한다. 같은 문구면 실패 |
| QA-194 | OCR 서버 앞에 인위적 10초 지연을 넣고 `연결 테스트` | **3초에 타임아웃 판정** (`✗ 타임아웃 (3s)`). 3초 시점에 스피너가 반드시 해제되고, 뒤늦게 도착한 응답이 결과 카드를 덮어쓰지 않는다 |
| QA-195 | OCR(:8000)만 중지, Spring(:8080)은 기동 → `연결 테스트` | API 행 `✓ Spring 응답 확인 (HTTP 401)` / OCR 행 `✗`. **두 서버가 분리 판정**되어 원인 지목이 가능하다 (RSK-24 대응의 핵심) |
| QA-196 | 로그인하지 않은 상태로 `연결 테스트` | API 행이 **401을 성공으로** 표시. 화면에 토큰·이메일·응답 바디가 렌더되지 않음 (NFR-015, SCR-31 금지 사항) |
| QA-197 | 연결 성공 확인 → 개발 PC의 LAN IP 변경(또는 다른 Wi-Fi로 이동) → 앱 재진입 후 전 탭 순회 → 진단 화면에서 새 IP 입력 후 blur | 순회 중 전 화면이 오류 상태 UI, 크래시 0. 새 IP 입력 후 **앱 재시작 없이** 즉시 정상 복구 (RSK-01 완화책의 실제 검증) |
| QA-198 | 오버라이드 상태에서 `기본값으로 되돌리기` 탭 | 두 입력칸이 `.env` 값으로 복원 + 토스트 `기본 서버 주소로 되돌렸습니다.` 앱 재실행 후에도 오버라이드가 부활하지 않음 |
| QA-199 | 기내모드 ON → 진단 화면 진입 | 오프라인 배너(G-5) + `연결 테스트` 버튼 비활성 + `오프라인입니다. 네트워크 연결을 확인해 주세요.` 서버 액세스 로그에 요청 **0건** (닿지 않을 요청을 쏘지 않는다) |
| QA-200 | IP 변경 후 앱 완전 종료 → 재실행 → 진단 화면 진입 | `mora.dev.apiBase` / `mora.dev.ocrBase` 가 복원되어 변경한 주소로 동작. 입력칸에 그 값이 채워져 있음 |
| QA-201 | **production APK**에서 설정(SCR-25) 버전 라벨 5회 탭, 이어서 `adb shell am start -a android.intent.action.VIEW -d "mora://dev/diagnostics"` | 두 경로 모두 아무 일도 일어나지 않음. 라우트 자체가 등록되지 않는다(`__DEV__ === false` && `EXPO_PUBLIC_ALLOW_SERVER_OVERRIDE !== '1'`). QA-184와 짝을 이룬다 |
| QA-202 | **FR-122 콜드/웜 동일 핸들러** — ① 앱 완전 종료 후 `adb shell am start -a android.intent.action.VIEW -d "mora://scan"` ② 앱을 포그라운드에 둔 채 같은 명령 | 두 경우 모두 같은 화면에 도달하고, 처리 로그가 **정확히 1회**만 남는다. `Linking.getInitialURL()`(콜드)과 `addEventListener('url')`(웜)이 같은 함수를 호출해 중복 내비게이션이 없다 |

**Phase 0 릴리스 게이트 등재** — [[Phases]] Phase 0 "사용자 확인(페이즈 종료 게이트)" 3항목에 다음을 **더한다.** 하나라도 실패하면 Phase 0을 닫지 않는다.

| 게이트 항목 | 근거 QA | 실패 시 의미 |
|---|---|---|
| 주소 오입력이 앱을 망가뜨리지 않는다 | QA-190, QA-191 | 팀원이 IP를 잘못 넣으면 복구 경로가 사라진다 |
| 실패 원인을 화면이 지목한다 | QA-193, QA-195 | RSK-24 대응 불가 — 데모 중 "앱 버그"와 "서버 미기동"을 구분할 수 없다 |
| 실패가 UI를 고착시키지 않는다 | QA-192, QA-194, QA-199 | 무한 스피너는 "서버 없음"보다 나쁜 진단 결과다 |
| IP 변경에서 재빌드 없이 복구된다 | QA-197, QA-198, QA-200 | RSK-01 완화책(FR-121)이 실물로 존재하지 않는다는 뜻 |
| 릴리스 빌드에 진단 화면이 없다 | QA-201 | 서버 주소 변경 경로가 최종 사용자에게 열려 있다 |
| 딥링크가 두 경로에서 같게 동작한다 | QA-202 | FR-122 미충족. Phase 3 이후 딥링크(DL-01~10) 전체가 이 위에 쌓인다 |

QA-190~QA-200 은 **`preview` APK**(진단 화면 존재)로, QA-201 은 **`production` APK**로 수행한다. 프로필을 섞으면 검증이 성립하지 않는다.

### 2-4. 테마 축 — 검증 매트릭스가 2배가 된다

**다크모드는 v1 In scope다.** 테마는 3택 — `시스템 따름`(기본값) / `라이트` / `다크`, 변경 지점은 설정(SCR-25) 세그먼트 하나([[ADR-004 Styling]] §4, [[Design Tokens]] §10). 종전 "v1 라이트 단일 테마" 전제로 작성된 이 절은 전면 교체되었고, 검증 목표도 뒤집혔다: **"OS가 다크여도 앱이 흔들리지 않는가"에서 "다크가 제대로 만들어졌는가"로 바뀌었다.**

#### 2-4-1. 산술을 먼저 적는다

| 검증 축 | 라이트 단일(구) | 다크 편입 후 | 배수 |
|---|---|---|---|
| 화면 케이스 | 31화면 | 31 × 2테마 = **62** | 2배 |
| 컴포넌트 갤러리 육안 검수 | CMP 50종 | 52 × 2 = **104** | 2배 |
| 회귀(§3) | REG 31항목 × 3기기 = 93 | 테마까지 곱하면 **186** | 2배 |
| 테마 자체 케이스 | 6행 | **THM-01 ~ THM-12** | 신규 |

**컴포넌트 104는 한 페이즈에 몰리지 않는다.** 두 테마 컴포넌트 검수는 **산출 시점 검수**다([[Requirements]] FR-128) — 각 페이즈가 그 페이즈에서 새로 만든 CMP를 양 테마로 검수하고 갤러리에 등재한다. 따라서 Phase 1이 **23종**(자기 산출 21종 + 테마 시스템 이전에 만들어진 Phase 0 소급 2종) × 2 = **46**을 처리하고, 남은 **29종 × 2 = 58**은 Phase 2~6에 분산된다(46 + 58 = 104). **Phase 7에 남는 것은 누적 52종의 검수 완료 여부 확인 하나뿐이다**(FR-112) — 이 페이즈에 52종을 새로 순회시키면 Phase 1 시점에 존재하지도 않는 31종을 분모에 넣었던 종전 모순이 반대 방향으로 되살아난다.

[[Design Tokens]] §10-7 과 [[ADR-004 Styling]] §결과 부정 7이 기록한 "Phase 7 QA 매트릭스 2배"의 실체가 위 표다. **62 화면검증과 186 회귀는 수동 QA 예산 밖이다** — 이 문서의 회귀 1회전이 이미 3기기 × 31항목이고, 여기에 테마를 곱하면 릴리스 게이트 한 번에 이틀이 더 붙는다.

#### 2-4-2. 두 개의 결정 — 곱하지 않고, 전수하지 않는다

**결정 1: 테마 축을 기기 축과 곱하지 않는다.** 테마 검증은 **DEV-02(중급) 1대**에서 두 테마를 돌린다. 근거 — 색은 OS 버전·SoC·화면비와 독립이고, 곱해서 늘어난 회차가 잡는 결함은 "다크 값이 틀렸다" 하나로 기기와 무관하다. 다만 **기기에 종속인 예외 2건은 곱한다**:

| 예외 | 기기 | 이유 |
|---|---|---|
| OLED 실물 검수 (THM-12) | OLED 패널 1대 | `#0F1621` 베이스 채택 근거(DK-01: 순수 검정의 스미어링·헤일로)는 OLED에서만 관측된다 |
| 시스템 크롬 색 동기화 (THM-07) | Android 15 (edge-to-edge 기본) | 상태바·내비바가 앱 배경과 어긋나면 흰 띠·검은 띠가 남는다. 이건 OS 버전 종속이다 |

**결정 2: 다크 전수 검증 대상은 31화면이 아니라 아래 P1 11화면(표 8행)이다.** 선별 기준은 **"색이 정보를 전달하는가"** 다. 배지·칩·상태색·표면 고도·이미지 매트가 있는 화면은 다크에서 깨지고, 텍스트+입력만 있는 화면(SCR-27 비밀번호 변경 등)은 토큰 2개(`text.primary`/`surface.input`)만 쓰므로 위험이 사실상 없다. P3는 케이스를 만들지 않고 회귀 순회 중 육안 스캔으로 대체한다.

### 2-5. 다크 명도대비 측정 절차 (THM-09)

다크 팔레트는 원본 참조 없이 신규 설계된 값이라 **"예쁜가"가 판정 기준이 될 수 없다. 대비비가 유일한 객관적 합격선이다**([[ADR-004 Styling]] §4 검증 기준). 문서 계산값과 실기기 렌더값이 어긋나는 원인은 넷뿐이다: (a) 하드코딩 HEX 잔존 (b) elevation/오버레이가 배경을 덮음 (c) 이미지 위 텍스트 (d) 기기 색 필터.

1. 기기에서 **야간 모드(블루라이트 필터)·색 보정·고대비 텍스트를 모두 OFF**, 밝기 50% 고정. 이 중 하나만 켜져 있어도 캡처 픽셀값이 토큰값과 달라져 측정이 무의미해진다.
2. 대상 화면을 다크로 띄우고 `adb exec-out screencap -p > shot.png` 로 **무손실 PNG** 캡처. 스크린샷을 메신저로 옮긴 파일은 압축으로 픽셀이 바뀌므로 금지.
3. 스포이드로 전경/배경 픽셀을 뽑는다. 텍스트는 **글자 획 중앙**에서 뽑는다(안티에일리어싱 경계에서 뽑으면 실제보다 낮게 나온다).
4. 두 HEX를 WCAG 2.1 상대휘도 대비비로 계산해 아래 기대값과 비교한다.

| # | 조합 | 기대 대비비 | 기준 |
|---|---|---|---|
| 1 | `text.primary` on `bg.base` | 15.42 | 4.5 |
| 2 | `text.muted` on `surface` (캡션 기본값) | 5.95 | 4.5 |
| 3 | `action` on `bg.base` (활성 탭·링크) | 6.53 | 4.5 |
| 4 | `text.inverse` on `action` (채움 버튼 라벨 — DK-05) | 6.53 | 4.5 |

| 7 | 마감 배지 fg/bg (라이트에서 가장 아슬아슬했던 4.6:1 조합) | 7.83 | 4.5 |
| 8 | `danger.strong` on `danger.container` (에러 박스 본문) | 8.73 | 4.5 |

## 5. 성능 측정 방법

### 5-1. 측정 대상과 예산

| ID | 지표 | 예산 (DEV-03 고사양) | 예산 (DEV-01 저사양) |
|---|---|---|---|
| PERF-01 | 콜드스타트 (TotalTime) | ≤ 2,500ms | ≤ 4,000ms |
| PERF-02 | 목록 스크롤 janky frames | < 5% | < 10% |
| PERF-03 | 메모리 PSS (보관함 / 카메라) | ≤ 250MB / ≤ 400MB | ≤ 200MB / ≤ 320MB |
| PERF-04 | release APK 크기 | ≤ 80MB (NFR-028) | 동일 |
| PERF-05 | 스캔 왕복 (촬영→결과) | P50 ≤ 5s, P95 ≤ 12s | P50 ≤ 7s |
| PERF-06 | 보관함 첫 데이터 표시 (LAN) | ≤ 1,500ms | ≤ 2,500ms |

측정은 전부 **`preview` 또는 `production` APK**로 한다. development 빌드는 Metro에서 번들을 받아오므로 콜드스타트가 무의미하다.

### 5-2. 콜드스타트 (PERF-01)

```bash
adb shell am force-stop com.mora.app
adb shell am start -W -n com.mora.app/.MainActivity
# 출력:
#   ThisTime: 1832
#   TotalTime: 1832   ← 이 값을 사용
#   WaitTime: 1901
```

5회 반복해 **중앙값**을 기록한다. 첫 실행(설치 직후)은 제외한다.

### 5-3. 프레임 드랍 (PERF-02)

```bash
adb shell dumpsys gfxinfo com.mora.app reset
# → 앱에서 200건 목록을 위→아래로 3회 스크롤
adb shell dumpsys gfxinfo com.mora.app
# 출력에서 확인:
#   Total frames rendered: 1240
#   Janky frames: 41 (3.31%)   ← 이 비율을 기록
#   50th / 90th / 95th / 99th percentile
```

보조 수단: 개발자 옵션 → **GPU 렌더링 프로파일 → 화면에 막대로 표시**. 초록 기준선(16ms)을 넘는 막대가 연속으로 나오면 문제다.

### 5-4. 메모리 (PERF-03)

```bash
adb shell dumpsys meminfo com.mora.app
# 출력 하단:
#   TOTAL PSS:  187432   ← KB 단위. /1024 = MB
```

측정 시점 3가지를 각각 기록한다: ① 홈 진입 직후 ② 보관함 200건 스크롤 후 ③ 카메라 프리뷰 활성 상태. ③ 이후 화면을 벗어나면 메모리가 회수되는지도 확인한다(누수 판정).

### 5-5. 네트워크 왕복 (PERF-05, PERF-06)

앱에 개발 빌드 전용 타이밍 로거를 둔다(요청 시작~응답 완료 ms). 서버 측은 OCR 서버가 이미 단계별 `log_timing` 을 남기므로 병목이 네트워크인지 추론인지 구분할 수 있다.

```bash
adb logcat -s MoraNet:V    # 앱 측 요청/응답 타이밍
# 서버 측: OCR 콘솔의 [TIMING] step / total 로그
```

### 5-6. APK 크기 (PERF-04)

```bash
ls -lh mora-v1.0.0-release.apk
unzip -l mora-v1.0.0-release.apk | sort -k1 -nr | head -20   # 큰 항목 20개
```

## 6. 자동화 방침

### 6-1. v1 결정

**v1은 수동 QA 중심 + 정적 게이트로 간다. E2E 자동화는 구축하지 않는다.**

### 6-2. 필수 게이트 (모든 커밋 / PR)

| 게이트 | 명령 | 실패 시 |
|---|---|---|
| 타입 체크 | `npx tsc --noEmit` (`npm run typecheck`) | 머지 금지. **Phase 0부터 유효** |
| 린트 | `npx eslint . --max-warnings=0` | 머지 금지. **Phase 1부터 유효** — ESLint 의존성이 Phase 0 시점에 아직 설치되지 않았다([[Tech Stack]] PKG-38) |
| 포맷 | `npx prettier --check .` | 머지 금지. **Phase 1부터 유효** (동일 사유) |
| 의존성 정합성 | `npx expo-doctor` | 경고 검토 후 진행 가능, 에러는 머지 금지 |
| **Tailwind 버전 고정** | `npm ls tailwindcss` → `3.4.x` | 머지 금지. NativeWind 4는 Tailwind 4를 지원하지 않고, 4가 들어오면 **오류 없이 색이 적용되지 않는다** ([[Risks]] RSK-33) |
| **app config 확장자** | `app.config.js` 가 존재하고 `app.config.ts` 가 없다 | 머지 금지. eas-cli ↔ TypeScript 6 충돌 ([[Risks]] RSK-34) |
| 하드코딩 색상 검사 | `grep -rn "#[0-9A-Fa-f]\{6\}" app/ src/ --exclude-dir=theme` → 0건 | 머지 금지 (Phase 1 이후) |
| 하드코딩 한국어 검사 | `grep -rn "['\"][가-힣]" app/ src/ --exclude-dir=i18n` → 0건 | 머지 금지 (Phase 7 이후) |
| **`dark:` 색 분기 검사** | `grep -rnE "dark:(bg\|text\|border)-" app/ src/` → 0건 | 머지 금지 ([[ADR-004 Styling]] §5-5 — 색은 CSS 변수가 이미 테마별로 갈린다) |
| **RN `useColorScheme` 직접 사용** | `grep -rn "useColorScheme" app/ src/ \| grep "react-native"` → 0건 | 머지 금지 (ADR-004 §5-6 — 3택 오버라이드를 모르는 훅이다. ESLint `no-restricted-imports` 로도 차단) |
| **테마 CSS 드리프트** | `npm run theme:css && git diff --exit-code global.css` | 머지 금지 ([[Design Tokens]] §13-0 — `global.css` 는 생성물이고 손으로 고치면 HEX가 두 곳에 존재한다) |

**다크 관련 3개 게이트**(`dark:` 색 분기 · RN `useColorScheme` · 테마 CSS 드리프트)는 다크모드 편입으로 신설되었고, **표 하단 2개**(Tailwind 버전 · app config 확장자)는 2026-07-27 Phase 0 실측으로 신설되었다. 후자 두 개는 **실패해도 오류가 나지 않는다**는 공통점이 있어 게이트로 잡는 것 외에 방법이 없다 — Tailwind 4는 색을 조용히 무시하고, `app.config.ts` 는 eas-cli를 부를 때까지 정상으로 보인다. **하드코딩 색상 검사 하나만으로는 다크 붕괴를 못 잡는다** — `dark:bg-black` 은 HEX가 아니라 grep을 통과하고, RN `useColorScheme()` 은 색을 쓰지 않지만 `시스템 따름` 이 아닌 사용자에게 틀린 테마를 준다. 세 개가 함께 있어야 THM-10의 수동 검수 부담이 줄어든다([[Risks]] RSK-31).

이 게이트들은 **로컬 실행이 수 초**이고 CI 없이도 강제할 수 있다. `package.json` 에 `"verify": "tsc --noEmit && eslint . --max-warnings=0 && prettier --check ."` 로 묶어 두고 커밋 전에 돌린다.

### 6-3. 왜 E2E 자동화를 v1에서 하지 않는가

1. **테스트 대상의 절반이 자동화 불가능하다.** 카메라 촬영, OS 권한 다이얼로그, 소셜 로그인 동의 화면, "출처를 알 수 없는 앱" 설치, 실기기 메모리·프레임 측정은 Detox/Maestro로 안정적으로 다룰 수 없거나 별도 인프라가 필요하다. 이 프로젝트의 핵심 가치(스캔)가 정확히 그 영역에 있다.
2. **백엔드가 3개 서버 + PostgreSQL + OpenAI 외부 의존이다.** 재현 가능한 E2E를 만들려면 시드 데이터 리셋 스크립트, OCR 모델 워밍업, LLM 응답 스터빙이 전부 필요하다. 이건 앱 개발과 맞먹는 작업량이다.
3. **화면 스펙이 페이즈마다 바뀐다.** 9화면을 이식하는 동안 셀렉터가 계속 흔들려 테스트 유지비가 기능 개발비를 넘어선다.
4. **회수 시점이 v1 이후다.** 자동화의 이익은 "같은 시나리오를 N번 반복"할 때 나온다. v1은 각 시나리오를 3~5회 돌리고 끝난다. 손익분기를 넘지 않는다.

대신 **수동 테스트의 반복 비용을 낮추는 데 투자한다**: 이 문서의 시나리오 표(단계/기대결과)를 그대로 체크리스트로 쓰고, 시드 데이터 생성 스크립트 1개(`scripts/seed.http` 또는 `seed.ps1`)를 만들어 매 회귀마다 동일한 상태에서 출발한다.

### 6-4. v1 이후 자동화 로드맵 (참고)

| 우선순위 | 대상 | 도구 | 조건 |
|---|---|---|---|
| 1 | 순수 함수 유닛 테스트 (필드 매핑, `Page<>` 언랩, `parsedJson` 추출, 이미지 URL 결합, 금액 파싱) | Jest | v1 중에도 저비용이라 **여유 있으면 지금 해도 됨** |
| 2 | 스모크 E2E 3플로우 (로그인 / 보관함 열람 / 검색) | Maestro (YAML, 셀렉터 단순) | 화면 스펙 확정 후 = Phase 7 이후 |
| 3 | 스캔 E2E | Maestro + 고정 이미지 주입(카메라 대신 갤러리 경로) | 시드 인프라 완성 후 |
| 4 | 성능 회귀 자동 측정 | `am start -W` + `gfxinfo` 스크립트화 | CI 러너에 실기기 연결 가능해질 때 |

**결정:** 위 1번(순수 함수 유닛 테스트)은 v1에서도 권장한다. 이 프로젝트는 `saveCard` 매핑, 이중 래핑 언랩, snake_case ↔ camelCase 변환처럼 **틀리기 쉽고 UI 없이 검증 가능한 로직**이 유난히 많아서, 이 부분만 Jest로 덮어도 수동 QA에서 잡아야 할 버그가 눈에 띄게 줄어든다.
