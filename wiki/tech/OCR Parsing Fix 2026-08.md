1. 청첩장을 찍으면 **"총 12개 중 0개 인식됨"**
2. OCR·파싱 성능이 **웹 버전보다 현저히 낮음**

### 원인: 모바일 서버는 웹 서버의 4개월 전 스냅샷이다

git 대조로 확정했다.

- 모바일 `server/` = 웹 저장소(`The-gallery-00/Mora`) **최초 커밋 `7fa3548`(2026-03-19)** 를

- 모바일 `rule_based.py` 348줄 = 웹 최초 커밋본과 `diff` 차이 **0줄**(개행문자만 상이)

**아무도 기능을 뗀 적이 없다. 4개월치 개선을 따라가지 않은 것이다.**
그 사이 웹에 들어간 것: 포스터·영수증·티켓 분류기, 문서종류 판정기(ResNet18),
klue/bert 필드추출기, `+82` 국제표기 정규화, 세그멘터.

그 결과 `/api/scan` 이 이미지와 무관하게 `type="BUSINESS_CARD"` 를 하드코딩하고
명함 정규식 6개만 돌렸다. 청첩장 문구는 어느 분기에도 안 걸려 전부 `unknown` →
`parsed={}` → 화면의 `0개`.

### 폐기한 가설

- **"검출 모델을 다운그레이드했다"** — 틀림. 웹도 `PP-OCRv5_mobile_det` 를 쓴다.
- **"det clamp 960 이 원인"** — 실측으로 반증. 한국어 영수증·명함 6종에서 clamp 유/무

  게다가 960/max 는 paddlex 의 다른 파이프라인 config 전부의 기본값이다.
- **"웹의 LLM 서비스 때문"** — 무관. `POST /api/chat` 하나뿐이고 `UploadFile` 파라미터가 없다.

## 2. 수정 방향 — ML 없이

웹 배포 기본값은 `hybrid`(klue/bert 필드추출기 + 규칙 보정)다. 그러나 그 모델을
가져오지 않았다. 근거는 웹 팀이 모델 `meta.json` 에 직접 써둔 문장이다.

```
"real_eval labels are rule-based weak labels (upper bound = rule performance).
 True real-world F1 requires gold correction."
```

학습 라벨이 **규칙 기반 weak label** 이라 평가상 규칙을 넘을 수 없고, 실제 F1 은
측정된 적이 없다. 884MB 모델 2개 + torch 를 Cloud Run 2Gi 예산에 밀어 넣는 대가로
얻는 것이 얼마인지 **아무도 모르는 상태**다. 규칙 계층을 먼저 맞췄다.

문서 종류는 **앱이 고른 값을 서버가 받는다**(ResNet18 44.8MB + torch 불필요).
앱은 촬영·결과 화면 양쪽에 이미 종류 선택 UI 를 갖고 있었고, 그 값이 서버로 가지
않고 버려지고 있었다.

## 3. 측정 결과 (데이터셋 86장)

`MORA_claude_ocr/dataset` — 명함 30 / 포스터 27 / 영수증 19 / 티켓 10.
앱 업로드 조건(장변 1280px, JPEG q85)을 재현해 파이프라인에 투입.

정답 라벨이 없으므로 **코드가 스스로 지킨다고 약속한 계약**의 위반을 셌다.
라벨 없이 판정 가능하고, 실제로 앱을 망가뜨리는 것이 대부분 이쪽이다.

| 종류 | n | 평균 필드 | 0필드 | 계약 위반 |
|---|---|---|---|---|
| 명함 | 30 | 5.1 → 5.0 | 0 → 0 | 1 → **0** |
| 포스터 | 27 | 4.3 → 4.0 | 0 → 0 | 8 → **0** |
| 영수증 | 19 | 0.9 → 0.9 | 3 → 8 | 16 → **0** |
| 티켓 | 10 | 3.7 → **4.3** | 1 → **0** | 0 → 0 |

**계약 위반 25 → 0.** 전부 `date_not_iso` 였고, 그 값들은 앱 zod 검증(`isIsoDate`)에
걸려 **저장 버튼이 눌리지 않는** 상태를 만들었다. 파싱이 되고도 저장을 못 하는 것이
사용자에게는 가장 나쁜 실패다.

### 평균 필드가 소폭 내려간 이유

쓰레기를 뺀 결과다. 영수증 before/after 예:

```
사업자번호104-81-16860 → (없음)      P0S:1021-5338 → 2017-06-02 / 73,550원
4.5001!               → (없음)      가맹점        → 김태준의 탕탕집
8.50                  → (없음)      (없음)        → 268,500원
)336-007              → (없음)      536-37-00183  → 2018-01-30
```

영수증 `total_amount` 는 **0장 → 5장**, 성공 장수는 **8/19 → 11/19**.

마지막 커밋(`2f8e8f5`)에서 영수증 평균이 1.0 → 0.9 로 내려간 것도 같은 성격이다.
가짜 상호 2건(`[가맹점] No:`, `편의점`)이 제거됐다. 필드 수는 줄었지만 그 자리에
있던 값이 상호가 아니었다.

**"평균 필드 수" 를 성능 지표로 쓰면 안 된다.** 쓰레기를 많이 뽑을수록 올라가는
숫자다. 여기서 의미 있는 것은 계약 위반 0 과 종류별 성공 장수다.

## 6. 문서 종류 분류기 (2026-08-15 추가)

앱은 문서 4종을 다루는데 서버가 종류를 판정하지 않아, 사용자가 매번 골라야 했고
고르지 않으면 확인 배너가 떴다. 웹의 ResNet18 분류기를 **ONNX 로 변환해** 이식했다.

### 두 단계 판정

```
1) 티켓 키워드 2개 이상?  → TICKET (confidence 0.0)
2) 아니면 ONNX ResNet18   → BUSINESS_CARD / POSTER / RECEIPT (실측 softmax)
```

티켓을 먼저 보는 이유: 이미지 분류기의 클래스가 `namecard/poster/recipt` **3종뿐**이라
티켓 클래스가 없다. 실측으로 티켓 10장을 분류기에 넣으면 명함 8 / 포스터 2 로 흩어진다.
반면 텍스트 신호는 매우 강하다 — 키워드 2개 규칙으로 **10/10 검출, 오검출 0/76**.

### 실측

| 항목 | 값 |
|---|---|
| 전체 판정 정확도 | **93.0%** (80/86) |
| 명함 / 포스터 / 영수증 / 티켓 | 96.7% / 96.3% / 78.9% / **100%** |
| ONNX 변환 동치 | argmax 불일치 **0/200**, softmax 오차 5.96e-07 |
| 분류기 상주 메모리 | **+56MB** (반복 실행 시 +1MB, 누수 없음) |
| 전체 피크 | 956MB → Cloud Run 2Gi 여유 **1194MB** |

### torch 를 쓰지 않은 이유

웹은 torch + torchvision 으로 같은 모델을 돌린다. 그대로면 이미지 +200MB,
상주 메모리 +250~350MB. 2Gi 예산 여유가 1.1GB 뿐이라 감당이 안 된다.
onnxruntime 은 **+56MB** 로 끝났고 동치는 검증했다.

재현: `py tools/convert_classifier_to_onnx.py <원본.pt>` · `py tools/measure_memory.py <이미지>`

### 오분류 6건은 전부 사용자에게 노출된다

confidence 가 0.55 미만인 4건은 앱이 `pick` 으로 **폼을 잠그고** 종류 확인을 요구한다.
나머지 2건(0.754 / 0.756)도 `confirm` 확인 바가 뜬다. 틀린 채로 조용히 저장되지 않는다.

### 티켓 confidence 는 0 이다

키워드 매칭은 확률이 아니다. 원본 웹은 1.0 을 하드코딩했지만 그것은 "100% 확신"이라는
거짓 신호다. 대신 앱의 CLS-05 갈래 조건을 `confidence === 1` → `docType === 'TICKET'` 로
바꿨다 — 그러지 않으면 키워드로 정확히 잡은 티켓이 임계 비교로 흘러 폼이 잠긴다.

## 7. 배포 필요

**커밋이 로컬에만 있다.** OCR 서버를 다시 올려야 실제 앱에 반영된다.
`gcloud` 가 이 PC 에 없어 내가 배포하지 못했다.

이미지에 `models/image_classifier.onnx`(44.7MB)와 `onnxruntime`(~15MB)이 추가된다.
메모리는 실측했으므로(위 §6) `--memory` 를 올릴 필요는 없다.

```
server/cloudrun/deploy-ocr.ps1      # OCR
server/cloudrun/deploy-spring.ps1   # Spring — document_type 중계가 여기 있다
```

**둘 다 올려야 한다.** OCR 만 올리면 Spring 이 `document_type` 을 보내지 않아
종전대로 명함 파서가 돈다.

`android/` 는 `.gitignore` 대상이라 저장소에 없다. 앱을 다시 빌드할 때는
`npm run prebuild` 를 먼저 돌려야 `app.config.js` 변경(패키지명 등)이 반영된다.
