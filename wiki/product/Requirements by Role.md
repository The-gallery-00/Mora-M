# Requirements by Role

[[Requirements]]의 FR-001~130 을 **담당 역할별로 묶은 작업용 뷰**. 팀원이 자기 것만 보고 검수·보완할 수 있게 자른 것이다.

상위: [[Home]]
관련: [[Requirements]] · [[Scope]] · [[Phases]] · [[Screen Specs]] · [[API Contract]]

## 0. 이 문서의 성격

| 항목 | 내용 |
|---|---|
| 정본 아님 | FR 의 **정본은 [[Requirements]]** 다. 이 문서는 같은 130건을 역할로 재분류한 뷰이며, 요구사항 문장이 다르면 [[Requirements]]가 이긴다. |
| **번호를 바꾸지 않았다** | FR-001~130 을 그대로 유지한다. 이 ID 는 이미 [[Screen Specs]]·[[Phases]]·[[Risks]]·[[QA Checklist]] 네 문서에서 참조되고 있어, 재번호하면 그 참조가 전부 무효가 된다. |
| 역할 = **소유자** | 그 요구사항의 **내용을 확정하고 결과를 검수할 책임자**다. 구현자가 아니다. 모바일 앱 구현은 앱 담당이 하고, 소유자는 "이게 맞다"를 판정한다. |
| 커버리지 | 130건이 **중복 없이 정확히 한 번씩** 배정되었다. 12 + 15 + 50 + 28 + 25 = 130. |

### 0-1. 신규 요구사항 발번 대역

기존 FR-001~130 이 이미 소진되었으므로 신규는 **200번대 이상**에서 시작한다.

| 역할 | 신규 대역 | 현재 |
|---|---|---|
| 기획 · OCR | `FR-200 ~ FR-299` | 미사용 |
| 백엔드 | `FR-300 ~ FR-399` | 미사용 |
| 프론트 | `FR-400 ~ FR-499` | 미사용 |
| 디자인 | `FR-500 ~ FR-599` | 미사용 |
| PM | 발번하지 않음 | 범위·우선순위 판정만 |

> 대역을 나눠두면 각자 동시에 추가해도 번호가 충돌하지 않는다. 합칠 때 재번호가 필요 없다.
> NFR 은 현재 NFR-029 까지 사용됨 → 신규는 `NFR-030` 부터, **PM 이 단독 발번**한다(전역 품질 기준이라 역할별로 쪼개면 중복된다).

### 0-2. 신규 1건 작성 형식

```markdown
| FR-201 | 명함 뒷면을 이어서 촬영해 한 건으로 합친다 |
|---|---|
| 소유자     | 기획 · OCR |
| 화면       | SCR-09, SCR-12 |
| API        | API-63 `POST /api/scan` |
| 우선순위   | P1 |
| 근거       | 결정: 실물 명함 다수가 뒷면에 영문 정보를 둔다 (원본에 해당 기능 없음) |
| 완료조건   | 앞·뒤 2장을 찍으면 저장된 명함 1건의 원문에 양면 텍스트가 모두 포함된다 |
```

`근거` 는 반드시 둘 중 하나로 시작한다 — `원본: <파일:행>` (확인한 사실) 또는 `결정: ...` (새로 정한 것).

## 6. 비기능 요구사항 (NFR) 소유

NFR 은 전역 품질 기준이라 역할별로 쪼개면 중복된다. **검수 책임만** 나눈다.

| 대역 | 영역 | 검수 책임 |
|---|---|---|
| NFR-001 ~ 008 | 성능 (콜드스타트, 프레임, 응답 피드백) | 프론트 |
| NFR-009 ~ 012 | 안정성 (크래시프리, 에러 복구) | 프론트 + PM |
| NFR-013 ~ 019 | 보안 · 프라이버시 (토큰 저장, cleartext, 스크린샷) | 백엔드 |
| NFR-020 ~ 024, 029 | 접근성 (터치 타겟, 명도 대비, 스크린리더) | 디자인 |
| NFR-025 ~ 028 | 호환성 (최소 API 26, 화면비, APK 용량 80MB) | PM |

신규 NFR 은 `NFR-030` 부터 **PM 단독 발번**.

## 7. 각자 오늘 할 일

1. 자기 섹션의 요구사항을 **위에서 아래로 읽고** 틀린 것·빠진 것을 표시한다.
2. 빠진 것은 **자기 신규 대역**(§0-1)에 §0-2 형식으로 추가한다.
3. `근거` 를 채울 수 없는 항목은 **정찰 대상** 파일을 실제로 열어 확인한다. 확인 안 되면 `결정:` 으로 적고 이유를 남긴다.
4. 우선순위에 이견이 있으면 P0/P1/P2 만 적어 PM 에게 넘긴다. 스스로 바꾸지 않는다.
5. 완료조건이 "구현한다" 로 끝나는 항목이 자기 섹션에 있으면 **관찰 가능한 문장으로 고친다.**
