# Scope — MORA 모바일 앱 v1

v1에 들어가는 것(In scope) · 명시적으로 빼는 것(Out of scope) · 나중으로 미루는 것(Deferred)의 3분류 확정표. 각 항목에 제외/포함 사유를 남긴다.

> **2026-07-27 범위 변경** — **다크모드가 Deferred D-17에서 In scope로 승격**되었다(§3-1 승격 기록). 대응 FR은 FR-123 ~ FR-129 신설 + FR-011/FR-019/FR-112 재작성이며 [[Requirements]]에 발번되어 있다. 같은 날 검색 문서유형 기본값이 확정되어 `전체` 옵션이 FR-130으로 In scope에 들어왔다. **유지되는 것**: APK 80MB(NFR-028) · 탭 4개 + 중앙 스캔 = 5슬롯 · Expo 관리형 · LAN IP 직결 · 9화면 전부 이식.

## 0. v1의 정의

> **v1 = 개발 PC의 LAN 백엔드에 붙어 동작하는, 서명된 Android release APK.** 원본 웹 9화면 전부를 모바일 네이티브 관례로 이식(→ SCR-01~30 + 개발 전용 SCR-31)하고, **라이트/다크 두 테마로** 렌더하며, 상업앱 수준의 품질 예산([[Requirements]] NFR)을 충족한다.

v1이 **아닌 것**: 스토어에 올라간 앱, iOS 앱, 클라우드 백엔드에 붙은 앱, 다중 사용자 실시간 협업 앱.

판정 기준 3가지 — 어떤 항목이 In scope인지 헷갈릴 때 이 순서로 판단한다.

1. **백엔드를 고쳐야 하는가?** → 고쳐야 하면 Out of scope. ([[ADR-002 Backend Connectivity]]의 무수정 원칙)
2. **원본 웹 9화면의 사용자 가치를 재현하는 데 필요한가?** → 필요하면 In scope.
3. **APK를 실기기에 설치해 검증하는 데 필요한가?** → 필요하면 In scope.

### 1-3. v1에서 **새로** 만드는 것 (웹에 없던 것)

백엔드에 API가 이미 있으므로 서버 수정 없이 구현 가능하다. 이것들이 "웹 이식"을 넘어서는 부분이다.

| 신규 기능 | 사용하는 API | 왜 v1에 넣는가 |
|---|---|---|
| 영수증 보관함 실 데이터 연결 (SCR-18) | API-49, 51, 53 | 웹은 목업 3건 하드코딩. 4종 문서 중 하나가 통째로 비어 있으면 제품이 성립하지 않는다 |
| 영수증 검색 | API-52 | 웹은 분기 누락으로 항상 0건. 서버는 정상 동작 중 |
| 알림 화면 + 미읽음 배지 (SCR-08) | API-32 ~ API-38 | 백엔드가 매일 09:00 KST 배치로 알림 row를 이미 생성 중인데 소비처가 없다 |
| 알림 설정 서버 저장 | API-39, API-40 | 웹은 localStorage만 사용 → 기기 간 동기화 불가 |
| 홈 대시보드 서버 조립 1회 호출 | API-24 | 웹은 3개 API를 각각 불러 클라이언트 조립. 모바일에서는 왕복 3회가 곧 지연 |
| 최근 검색어 | API-54 | 검색 진입 마찰 감소. 서버에 기록이 이미 쌓이고 있다 |
| 무한 스크롤 | 모든 목록 API의 `page`/`size` | 웹은 첫 페이지만 조회해 20건 초과분이 열람 불가 |
| 명함 그룹 이름 변경 | API-22 | 그룹 생성·삭제만 있고 수정이 빠져 있었다 |
| 이미지 뷰어(핀치줌) (SCR-21) | API-64 | 포스터·영수증의 작은 글씨 판독에 필수 |
| 공유 시트 수신 | — | 모바일 고유 가치([[PRD]] V-2) |
| 연속 스캔 | — | PS-1 지훈 페르소나의 핵심 시나리오 |
| 이용약관·개인정보 처리방침 (SCR-30) | — | 웹은 TODO 상태. 배포 전 필수 |
| **라이트/다크 2테마 + 3택 설정 (SCR-25)** | — | 웹 설정에 `theme` 값이 있으나 `data-theme` 속성만 세팅하고 **대응 스타일이 없어 무동작**이었다. 앱이 이 기능의 첫 실사용 구현이며, 다크 팔레트는 참조할 원본이 0이라 신규 설계다([[PRD]] V-9) |
| **검색 문서유형 `전체` 병렬 검색** | API-19, 47, 52, 61 | 서버에 통합 검색 엔드포인트가 없어 웹에는 개념 자체가 없었다. 4종을 `Promise.allSettled`로 묶어 앱이 합성한다. 기본값이 아니라 명시 선택 전용(FR-069/FR-130) |

#### 1-4-1. iOS — 출시 안 함, 호환은 유지 (2026-07-28 결정)

출시 대상은 Android 뿐이지만 **나중에 iOS 를 켤 수 있는 상태를 유지**한다. 지키는 것은 세 가지뿐이고 추가 비용은 거의 없다.

| 지킬 것 | 이유 |
|---|---|
| Android 전용 네이티브 모듈을 쓰지 않는다 | 현재 채택한 패키지는 전부 iOS 를 지원한다. 대체 불가한 Android 전용 모듈을 넣는 순간 iOS 경로가 막힌다 |
| `Platform.OS` 분기를 한 곳에 모은다 | 화면 코드에 흩뿌리면 나중에 iOS 분기를 추가할 지점을 찾지 못한다 |
| iOS 에서 다르게 동작하는 지점을 **주석으로 남긴다** | SecureStore(Keychain), ATS(평문 HTTP 차단), OAuth 콜백(`ASWebAuthenticationSession`), 권한 문구(Info.plist), 하드웨어 백버튼 부재 |

**하지 않는 것**: iOS 빌드·실기기 검증·App Store 등록·Apple 개발자 계정. 이건 [[Scope]] Deferred D-4 로 남는다.

#### 1-4-2. 백엔드 접속 — 2단계 (2026-07-28 결정)

Play Store 배포가 확정되면서 **LAN IP 직결만으로는 끝낼 수 없게 되었다.** 스토어에서 앱을 받은 사용자의 폰은 개발 PC 와 같은 네트워크에 없다.

| 단계 | 접속 방식 | 빌드 프로파일 | cleartext |
|---|---|---|---|
| 개발·내부 테스트 | 개발 PC LAN IP 평문 HTTP | `development` · `preview` | 허용 |
| **스토어 배포** | **클라우드 HTTPS 도메인** | `production` | **차단** |

**클라우드 배포는 앱 팀의 산출물이 아니라 선행 조건이다.** 이것이 풀리지 않으면 스토어 제출 자체가 불가하다 — [[Risks]] 및 Deferred D-1 참조. 앱 코드는 `EXPO_PUBLIC_API_URL` / `EXPO_PUBLIC_OCR_URL` 두 환경변수만 바꾸면 전환되도록 이미 설계되어 있다([[ADR-002 Backend Connectivity]]).

## 2. Out of scope (v1에서 명시적으로 제외)

여기 있는 항목은 "아직 안 함"이 아니라 **v1에서는 하지 않기로 확정**한 것이다. 요청이 들어와도 이 표를 근거로 거절한다.

### 2-1. 플랫폼·배포

| 항목 | 제외 사유 |
|---|---|
| **iOS 빌드·출시** | Apple 개발자 계정·인증서·프로비저닝·실기기가 전제인데 현재 없다. **다만 코드 호환은 유지한다** — §1-4-1. 빌드·검증·등록만 제외한다 |
| **홈 화면 위젯 (Android / iOS)** | Expo 관리형 워크플로 밖이다. Android Glance(Kotlin) + iOS WidgetKit(SwiftUI) 네이티브 코드와 앱↔위젯 데이터 공유(App Group / SharedPreferences)를 각각 직접 작성해야 한다. **1차 앱을 실제로 써본 뒤 개발 여부를 판단**하기로 결정(2026-07-28) |
| **기기 캘린더 쓰기 (expo-calendar)** | 서버 측 Google Calendar 연동(FR-095·096)과 별개 기능이다. 권한·중복 등록·시간대·종일 일정 처리가 추가로 필요하다. 일정 기능이 서버에서 먼저 안정된 뒤 판단한다 |
| **태블릿·폴더블 전용 레이아웃** | 대상 사용자는 폰 단일. 320~480dp 폭만 보장하고 그 이상에서는 폰 레이아웃을 그대로 늘린다 |
| **가로 모드(landscape)** | 촬영·목록·폼 모두 세로에 최적화되어 있고, 가로를 지원하면 31화면 × 2방향 검증 비용이 발생한다. **다크모드 편입으로 QA 매트릭스가 이미 31화면 × 2테마로 2배가 되었으므로**(FR-112), 방향까지 곱하면 4배가 된다 — v1 일정에서 감당할 수 없다. 카메라 촬영 시 EXIF 회전 보정은 서버가 이미 수행한다 |
| **Wear OS / TV / Auto** | 해당 없음 |

### 2-2. 데이터·동기화

| 항목 | 제외 사유 |
|---|---|
| **실시간 동기화 (WebSocket / SSE / 푸시 스트림)** | 백엔드에 실시간 전송 코드가 전혀 없다(알림도 DB row 생성 + 폴링 방식). 서버 수정 없이는 불가능하며, 무수정 원칙을 어긴다. v1은 pull-to-refresh + 화면 진입 시 재조회로 대체 |
| **다중 기기 충돌 해결(conflict resolution)** | 백엔드에 `updatedAt` 기반 낙관적 잠금이나 ETag/If-Match가 없다. 명함 엔티티는 아예 `updatedAt` 컬럼조차 없다. 충돌 감지 수단 자체가 없으므로 v1은 **last-write-wins**를 명시적으로 채택하고, 이를 사용자에게 숨기지 않는다 |
| **오프라인 쓰기(오프라인 큐 · 로컬 우선 저장 후 동기화)** | 저장 경로가 이미지 커밋(OCR 서버) → 문서 저장(Spring) 2단계 비원자적 트랜잭션이고, 백엔드에 보상 트랜잭션·멱등키가 없다. 오프라인 큐를 넣으면 고아 이미지·중복 레코드가 대량 발생한다. v1은 **오프라인 읽기 전용**(FR-101) |
| **로컬 전체 DB 미러링(SQLite/WatermelonDB)** | 위와 같은 이유. v1의 오프라인은 HTTP 응답 캐시 + 이미지 디스크 캐시 수준으로 한정 |
| **문서 내보내기(CSV/vCard/PDF)** | 백엔드 지원 없음. 클라이언트 단독 구현은 가능하나 v1 핵심 루프 밖 |
| **연락처 앱 자동 저장** | 원본 웹 설정에 `연락처` 토글이 있으나 **연결된 API가 없는 UI뿐인 토글**이었다. 서버 스펙이 없으므로 구현 근거가 없다 |

### 2-3. 기능

| 항목 | 제외 사유 |
|---|---|
| **푸시 알림(FCM) 실제 수신** | 백엔드에 디바이스 토큰 저장 컬럼·엔티티가 전혀 없고(`User`/`NotificationSetting` 어디에도 없음), 푸시 전송 코드도 없다. 서버 수정 없이 불가능. v1은 **인앱 알림 목록 + 미읽음 배지**까지만 |
| **프로필 사진 업로드** | 서버에 `/me/avatar` 엔드포인트가 존재하지 않는다. 원본 웹은 base64를 localStorage에만 저장하는 임시 구현이었고, 이를 이식하면 기기 저장소를 낭비하면서 서버와 불일치하는 상태만 만든다 |
| **서버 로그아웃(토큰 무효화)** | `/auth/logout` 엔드포인트가 없다. JWT가 stateless·리프레시 토큰 없음 구조라 서버가 무효화할 방법 자체가 없다. v1은 클라이언트 파기만 수행 |
| **토큰 자동 갱신(refresh token)** | 백엔드에 리프레시 토큰 발급/교환 엔드포인트가 없다. JWT 만료는 24시간 고정. v1은 만료 시 재로그인 유도(FR-030)로 대응 |
| **영수증 품목(items) 입력·표시** | OCR 파서가 items를 만들지 않고(`ParsingSkill`이 해당 키를 반환하지 않음), 프론트도 `items: []`를 보내며, `receipt_items` 테이블은 비어 있다. 데이터가 존재하지 않는 UI는 만들지 않는다 |
| **가계부 수입/지출 원장 화면** | 원본 웹의 `INCOME`/`EXPENSE`, 카테고리, 결제수단, 예산 잔액은 **DB 스키마에 없는 UI 전용 목업 개념**이다. 서버에 필드가 없으므로 구현 불가. v1의 SCR-18은 일반 문서 목록으로 만든다 |
| **명함 12필드 전체 저장** | 서버 `BusinessCard` 엔티티에 `english_name / department / office_phone / fax / address / website / zip_code` 컬럼이 없다. OCR이 추출하고 편집 화면에 표시되지만 저장 시 `rawOcrText`에만 남는다. v1은 이 사실을 사용자에게 숨기지 않고, 저장되는 5필드를 시각적으로 구분한다 |
| **문서 유형 `ETC` 저장** | 서버 저장 경로가 4종만 지원한다. v1은 저장 차단 + 유형 변경 유도(FR-050) |
| **명함 OCR 재학습 / 모델 관리 UI** | 서버 운영 영역. 앱 관심사 아님 |
| **관리자·통계 대시보드** | 대상 사용자 아님 |
| **소셜 공유(문서를 외부로 내보내기)** | v1은 공유 시트 **수신**만 지원(FR-052). 발신은 개인정보(명함 연락처) 유출 경로가 되므로 정책 검토 후 결정 |
| **다국어 실제 번역(en/ja 등)** | 사용자 전원이 한국어 사용자. v1은 i18n 키 추출 구조만 준비(FR-111)하고 로케일은 `ko` 단일 |
| **위젯 / 퀵 액션 / 앱 숏컷** | 핵심 루프 검증 후 판단 |

## 5. 범위 변경 절차

1. 변경 요청은 **이 문서의 표에 행을 추가하는 형태**로 제안한다(구두 합의만으로 범위를 늘리지 않는다).
2. In scope로 승격하려면 대응하는 **FR ID를 [[Requirements]]에 신규 발번**하고, 완료 조건과 담당 페이즈를 함께 적는다.
3. 페이즈가 이미 시작된 뒤의 승격은 해당 페이즈가 아니라 **다음 페이즈**에 배치한다. 진행 중 페이즈의 완료 정의를 바꾸지 않는다.
4. Out of scope 항목을 되살릴 때는 "제외 사유"가 해소되었음을 근거와 함께 표에 기록한다.
