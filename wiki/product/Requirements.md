# Requirements — MORA 모바일 앱

기능요구 FR-001~FR-130, 비기능요구 NFR-001~NFR-029, 그리고 FR ↔ 화면 ↔ API ↔ 페이즈 추적 매트릭스. **FR/NFR ID의 단일 진실 원본**이다.

> **2026-07-27 개정** — 사용자 결정으로 **다크모드가 v1 In scope로 편입**되었다(종전 "v1 라이트 고정" 폐기). 영향: FR-011 재작성 · FR-019/FR-112 재작성 · **FR-123~FR-129 신설** · NFR-021/NFR-027 재작성 · **NFR-029 신설**. 같은 날 검색 문서유형 기본값이 확정되어 FR-069/FR-071 재작성 + **FR-130 신설**. 결정문은 [[ADR-004 Styling]] §4, 값의 정본은 [[Design Tokens]] §10·§13.

> **2026-07-27 정합성 개정 (검수 분모)** — FR-128이 Phase 1에서 "CMP 전부"의 두 테마 검수를 요구했는데, [[Component Library]] §1-I·[[Phases]] §6이 확정한 **Phase 1 신규 CMP는 21종**(나머지 31종은 Phase 2~6 산출)이라 분모가 모순이었다. **두 테마 검수는 "산출 시점 검수"로 확정한다** — 각 페이즈는 자기 페이즈에서 새로 만든 CMP를 라이트/다크 양쪽에서 검수하고 갤러리에 등재한다. 따라서 **FR-128의 Phase 1 분모 = 21종**이고, **누적 52종 전체의 검수 완료는 Phase 7 게이트(FR-112)** 가 확인한다. 신규 FR 발번은 하지 않았다(총계 **130** 유지) — Phase 7 누적 게이트는 이미 Phase 7 다크 마감 요구인 FR-112의 완료조건으로 흡수했다.

## 0. 읽는 법

### 0-1. ID 체계

| 접두사 | 대상 | 범위 | **정본 문서** |
|---|---|---|---|
| `FR-###` | 기능 요구사항 | FR-001 ~ FR-130 | **이 문서** |
| `NFR-###` | 비기능 요구사항 | NFR-001 ~ NFR-029 | **이 문서** |
| `SCR-##` | 화면 | SCR-01 ~ SCR-31 | [[Screen Specs]] (이 문서 §0-3은 미러) |
| `API-##` | 엔드포인트 | API-01 ~ API-67 | [[API Contract]] |
| `CMP-##` | 공통 컴포넌트 | CMP-01 ~ CMP-52 | [[Component Library]] |
| `US-##` / `EP-#` | 유저스토리 / 에픽 | US-01~40 / EP-1~8 | [[User Stories]] |
| `RSK-##` | 리스크 | RSK-01 ~ | [[Risks]] |

ID는 **재사용하지 않는다.** 요구사항이 폐기되면 번호를 비우지 않고 표에 `폐기` 상태로 남긴다.

FR-001~FR-120은 **페이즈 순서대로 연속 배정**되어 있다(§3-3 롤업 참조). 대역이 꽉 차 있으므로 신규 요구사항은 대역 중간에 끼워 넣지 않고 **최대 번호 뒤에 이어 발번**하고 담당 페이즈를 표에 명시한다. 현재 최대는 **FR-130 / NFR-029**이며 다음 발번은 FR-131 · NFR-030이다. 다른 문서(특히 [[Phases]] · [[Screen Specs]] · [[Risks]])는 FR을 참조만 하고 발번하지 않는다.

**연속 배정 대역 밖 FR의 담당 페이즈** (§3-3 롤업이 정본)

| FR | 담당 페이즈 | 사유 |
|---|---|---|
| FR-121, FR-122 | Phase 0 | 기반 셋업 — 진단 화면·딥링크 스킴 |
| FR-124 ~ FR-128 | Phase 1 | **테마 기반** — 토큰 2벌·영속·시스템 추종·시스템 크롬·CMP 검수는 디자인 시스템의 일부다. FR-128의 Phase 1 검수 분모는 **Phase 1 산출 21종**이며, 누적 52종 게이트는 Phase 7의 FR-112다 |
| FR-130 | Phase 5 | 검색 화면 소속 |
| FR-123 | Phase 6 | 설정 화면(SCR-25)이 Phase 6에 만들어진다. Phase 1~5 동안의 테마 전환 수단은 FR-128의 개발 갤러리 토글 |
| FR-129 | Phase 7 | **화면별 다크 마감·회귀** |

### 0-4. API ID 대역

**API ID의 정본은 [[API Contract]]다** (API-01 ~ API-67). API-01~62는 Spring 백엔드(`:8080`) 컨트롤러 14개의 엔드포인트, API-63~67은 OCR 서버(`:8000`) 직결 경로다.

| ID | 메서드 | 경로 | 앱 사용 | 비고 |
|---|---|---|---|---|
| API-63 | POST | `{OCR_BASE}/api/commit` | **사용** | 결정: Spring 미경유 직접 호출. 이유 — 백엔드 무수정 원칙([[ADR-002 Backend Connectivity]])상 프록시를 추가할 수 없다. 인증 없는 엔드포인트라는 위험은 [[Risks]]에 등재 |
| API-64 | GET | `{OCR_BASE}/uploads/{TYPE}/{filename}` | **사용** | 모든 문서 이미지의 실제 소스. 정적 서빙 |
| API-65 | GET | `{OCR_BASE}/` | **사용** | 헬스체크. `{"service":"MORA OCR Service","version":"3.0"}` 고정 응답으로 연결 진단 판정([[Networking]]) |
| API-66 | POST | `{OCR_BASE}/api/ner-label` | 미사용 | NER 라벨링 보조 경로. 앱 관심사 아님 |
| API-67 | POST | `{OCR_BASE}/api/scan` | 미사용 | 앱은 Spring 경유 API-41을 쓴다(인증·이중래핑 일관성) |

### 세션 유지 방식 — 리프레시 토큰을 도입하지 않는다 (2026-07-28 결정)

**현황(코드 확인)** — 백엔드에 사용자 인증용 Refresh Token 이 **존재하지 않는다.** `com.mora` 에서 "refresh" 로 검색되는 3개 파일(`GoogleTokenResponse` · `GoogleCalendarToken` · `GoogleCalendarService`)은 전부 **Google Calendar OAuth 용**이며 사용자 세션과 무관하다. JWT 는 `app.jwt-expiration` 단일 만료값으로만 관리된다(`security/JwtUtil.java`).

**검토한 두 안**

| 안 | 백엔드 작업 | 앱 작업 | 보안 |
|---|---|---|---|
| A. Access/Refresh 2단 | 테이블 + `POST /auth/refresh` + 폐기 로직 + 로그인 응답 변경 | 인터셉터 + **동시 401 큐잉** | 탈취 시 서버가 즉시 무효화 가능 |
| **B. JWT 만료 연장 (채택)** | **설정 1줄** (`app.jwt-expiration` → 14일) | 없음 (기존 자동 로그인 그대로) | 만료 전까지 무효화 불가 |

**B 채택 근거** — (1) 백엔드 코드 변경이 0이라 Phase 2 를 막지 않는다. (2) MORA 는 금융·결제 앱이 아니라 개인 명함 보관함이고, 저장 데이터에 결제수단·주민번호가 없다. (3) A 의 실제 난이도는 서버가 아니라 **앱의 동시 401 큐잉**에 있고, 여기서 버그가 잘 난다 — v1 에서 감수할 위험이 아니다.

**만료 14일을 고른 이유** — 24시간은 모바일에서 사용 불가, 30일은 탈취 시 노출 창이 과도하다. 명함 스캔은 사용 빈도가 낮은 앱이라 14일이면 대부분의 사용자가 재로그인을 거의 겪지 않는다. **재로그인이 잦다는 피드백이 나오면 30일로 올리되, 아래 대가를 다시 승인받는다.**

**수용하는 대가 (반드시 [[Auth]] 에 명시)**

- 토큰이 탈취되면 **만료까지 최대 14일간 무효화할 수 없다.**
- **로그아웃은 서버 세션을 끊지 않는다.** 로컬 SecureStore 에서 지우는 것뿐이며, 그 전에 복사된 토큰은 계속 유효하다.
- 비밀번호를 변경해도 기존 토큰이 살아 있다.

**재검토 트리거** — 결제·민감정보가 도입될 때, 또는 토큰 유출 사고가 실제로 발생할 때. 그때 A 안으로 전환한다. FR-132 가 그 전환 비용을 낮추기 위한 사전 조치다.

**2026-07-27 개정 전후 차이** — 총 122 → **130**(+8: FR-123~FR-130), P0 73 → **81**(+8). 증분 8건 중 다크모드가 7건(FR-123~FR-129), 검색 `전체` 옵션이 1건(FR-130)이다. P0가 8건 늘어난 이유: 다크모드는 "있으면 좋음"이 아니라 v1 필수 기능으로 확정되었고(§0-2 P0 판정 기준), 기존 FR-011·FR-112는 P1 → **P0으로 승격**되었다. P1/P2 합계는 변동 없다 — 승격된 2건이 P1에서 빠지고 FR-129·FR-130이 P1로 들어와 상쇄된다.

**다크모드 작업량 반영** — 페이즈 개수만으로는 부하가 드러나지 않으므로 명시한다: Phase 1은 토큰 2벌 정의 + CSS 변수 배선 + **Phase 1 산출 CMP 21종(+ Phase 0 소급 2종) × 2테마 검수**로 **≈1.5배**, Phase 7 QA 매트릭스는 31화면 × 2테마로 **2배**다([[Design Tokens]] §10-7, [[ADR-004 Styling]] §결과 부정 6~7). 컴포넌트 검수 총량은 누적 **52종 × 2 = 104**지만 산출 시점 검수(FR-128)로 페이즈에 분산되므로 한 페이즈에 몰리지 않는다 — Phase 7에 남는 것은 누적 완료 확인(FR-112)뿐이다.
