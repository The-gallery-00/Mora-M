# ADR-003 Navigation

expo-router(파일 기반 라우팅)를 채택하고, **하단 탭 4개(홈·보관함·검색·설정) + 중앙 스캔 액션 = 5슬롯** + 3계층 오버레이(스택 push / 모달 / 바텀시트) 구조로 웹 9화면을 재배치한다.

상위: [[Architecture]]
관련: [[Navigation Map]] · [[Screen Specs]] · [[Mobile UX Guide]] · [[Auth]] · [[ADR-001 Framework]] · [[Directory Structure]]

## 맥락

| 사실 | 내용 | 근거 |
|---|---|---|
| 웹 IA | 상단 고정 헤더 하나에 로고·통합검색바·업로드·보관함 드롭다운·알림·프로필·로그아웃 **7개 액션**이 몰려 있다 | 원본: `app/dashboard/layout.tsx` |
| 웹 라우트 | `/`, `/login`, `/signup`, `/dashboard`, `/upload`, `/search`, `/settings`, `/storage/{cards,tickets,posters,receipts}` = 11개 | 원본: `app/` 트리 |
| 인증 게이트 | `app/dashboard/layout.tsx` **한 곳**에서만 처리 | 동일 |
| 보관함 | 4개 라우트가 드롭다운으로 연결. 화면 구조는 서로 거의 같다 | 원본: `storage/*/page.tsx` |
| 챗봇 | 전역 플로팅 패널. 드래그 이동, hover 툴팁 3종 — 데스크톱 전용 | 원본: `components/common/ChatbotWidget.tsx` |
| 팀이 이미 그린 정답 | 랜딩 페이지의 폰 목업 `PhoneDashboard` 하단 탭바 = `홈` `업로드` `보관함` `설정` | 원본: `app/page.tsx` |
| 목업의 보관함 | 상단 가로 스크롤 필터 칩 `전체` `명함` `티켓` `영수증` `포스터` | 원본: `app/page.tsx` `ListScreen` |
| OAuth 콜백 | 백엔드가 `{FRONTEND_URL}/dashboard?token=...&userId=...` 로 리다이렉트하는 HTML 브리지 | 04-api §3-5 |

해결해야 할 질문 3가지:
1. 라우팅 라이브러리를 파일 기반으로 갈 것인가 명령형으로 갈 것인가.
2. 웹의 상단 7액션 헤더를 모바일 IA로 어떻게 재배치할 것인가.
3. 상세·편집·스캔·챗봇을 push / modal / sheet 중 무엇으로 띄울 것인가.

## 검토한 대안

### A. 라우팅 라이브러리

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| **expo-router** (React Navigation 위의 파일 기반 레이어) | 파일 트리 = 라우트 트리라 원본 Next.js App Router 구조를 그대로 옮길 수 있다. 딥링크가 파일 경로에서 **자동 생성**(OAuth 콜백에 결정적). 레이아웃 라우트(`_layout.tsx`)로 인증 게이트를 한 곳에 둘 수 있다(웹과 동일한 패턴). 타입 안전 라우트 생성 | 라우트 그룹·플랫폼 분기 등 파일 규약 학습 필요. 동적 라우트 조합이 복잡해지면 명령형보다 우회가 번거로움 | **채택** |
| React Navigation 직접 사용 | 완전한 통제. 중첩 네비게이터 구성이 명시적 | 딥링크 `linking` 설정을 손으로 유지해야 한다. 라우트 추가마다 3곳(네비게이터·타입·linking)을 고쳐야 함. Next.js 경험 전이 없음 | expo-router가 결국 이 위에 얹히므로 **내려갈 이유가 없다.** 필요하면 `Stack.Screen` 옵션으로 동일 통제가 가능 |
| 단일 스택 + 조건부 렌더 | 최소 구성 | 탭·모달·백스택·딥링크를 전부 자작해야 함. "상업앱 수준" 목표와 충돌 | 자작 비용만 발생 |

### B. 정보 구조(IA)

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| **탭 4개 + 중앙 스캔 액션** — `홈` `보관함` (스캔) `검색` `설정` | 팀 목업(홈/업로드/보관함/설정)을 계승하면서, 업로드는 "화면"이 아니라 "행동"이므로 중앙 액션으로 승격. 웹 헤더의 통합검색바가 갈 곳(검색 탭)을 얻는다. 5슬롯은 Android/iOS 공통 관례 | 슬롯이 5개라 좁은 기기에서 라벨이 빡빡함 | **채택** |
| 탭 4개 그대로 (`홈` `업로드` `보관함` `설정`) | 목업과 100% 일치. 가장 단순 | 검색이 탭에 없어 홈 헤더 아이콘으로 밀린다. 검색은 이 앱의 핵심 가치(벡터 검색·자연어 검색)인데 2급 시민이 된다. 업로드가 탭이면 뒤로가기 시 반쯤 진행된 스캔 상태가 탭에 남는다 | **검색 강등**과 **스캔 상태 잔존** 문제 |
| 탭 5개 (`홈` `보관함` `스캔` `검색` `설정`, 스캔도 일반 탭) | 구현 단순 | 스캔은 상태를 가진 선형 플로우(촬영→크롭→검토→저장)다. 탭으로 두면 중간 상태에서 다른 탭으로 갔다가 돌아왔을 때의 기대가 모호해진다 | 스캔은 **모달 플로우**여야 한다 |
| 보관함 4탭 분리 (명함/티켓/포스터/영수증) | 웹 라우트와 1:1 | 탭 8개. 불가능 | — |
| 드로어(햄버거) | 항목 수 제약 없음 | Android에서도 하단 탭이 표준이 된 지 오래. 한 손 조작에서 상단 햄버거는 도달성이 나쁨 | 관례 위배 |

### C. 상세·편집 표현

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| **혼합 3계층** — 목록→상세는 push, 스캔/챗봇은 fullScreenModal, 확인/선택/경량 상세는 바텀시트 | 각 상황에 맞는 관례. 뒤로가기 의미가 명확 | 규칙을 문서화하지 않으면 팀이 제각각 쓴다(그래서 아래 §결정에 규칙표를 둔다) | **채택** |
| 전부 push | 단순 | 삭제 확인, 문서 종류 선택 같은 경량 상호작용에 화면 전환은 과하다 | 과설계 |
| 전부 바텀시트 (웹 `StorageDrawer` 직역) | 원본과 유사 | 명함/포스터는 필드가 8~12개 + 이미지라 시트 92%를 채운다. 그럴 바엔 화면이다. 시트 안 키보드 회피는 별도 처리가 필요해 버그가 잦다 | 필드 많은 문서에서 무너짐 |

## 결정

### 1. expo-router 채택, 라우트 그룹 3개

```
app/
├── _layout.tsx                 # QueryClient·테마·세션 부팅. 스플래시 유지 게이트
├── (auth)/                     # 미인증 전용
│   ├── _layout.tsx             #   authed 이면 (app) 으로 replace
│   ├── landing.tsx             #   SCR: 랜딩(온보딩 흡수)
│   ├── login.tsx
│   └── signup.tsx
├── (app)/                      # 인증 필수
│   ├── _layout.tsx             #   guest 이면 (auth)/login 으로 replace  ← 웹의 dashboard/layout 대응
│   ├── (tabs)/
│   │   ├── _layout.tsx         #   하단 탭 4(홈·보관함·검색·설정) + 중앙 스캔 액션 = 5슬롯
│   │   ├── index.tsx           #   홈(대시보드)
│   │   ├── storage.tsx         #   보관함 (종류 필터 칩 통합)
│   │   ├── search.tsx          #   검색
│   │   └── settings.tsx        #   설정
│   ├── document/[type]/[id].tsx#   문서 상세/편집 (push)
│   ├── cards/groups.tsx        #   명함 그룹 관리 (push)
│   ├── notifications.tsx       #   알림 목록 (push)
│   ├── scan/                   #   스캔 플로우 (모달 스택)
│   │   ├── _layout.tsx
│   │   ├── camera.tsx
│   │   ├── adjust.tsx
│   │   ├── review.tsx
│   │   └── done.tsx
│   └── chat.tsx                #   챗봇 전체화면 (모달)
└── +not-found.tsx
```

인증 게이트는 `(auth)/_layout.tsx`와 `(app)/_layout.tsx` **두 곳에만** 둔다. 개별 화면에 가드를 넣지 않는다(웹과 동일한 원칙).

### 2. 하단 탭 구성

| 슬롯 | 라벨 | 라우트 | 웹 대응 |
|---|---|---|---|
| 1 | 홈 | `(tabs)/index` | `/dashboard` |
| 2 | 보관함 | `(tabs)/storage` | `/dashboard/storage/{cards,tickets,posters,receipts}` **4개를 1개로 통합** |
| 3 | (중앙 액션) | `scan/camera` 를 모달로 push | `/dashboard/upload` |
| 4 | 검색 | `(tabs)/search` | `/dashboard/search` + 헤더 통합검색바 |
| 5 | 설정 | `(tabs)/settings` | `/dashboard/settings` + 프로필/로그아웃 |

- **보관함 통합**: 상단 가로 스크롤 필터 칩 `전체` `명함` `티켓` `포스터` `영수증`. 팀 목업 `ListScreen`이 제시한 구조 그대로다. 웹 헤더의 보관함 드롭다운(키보드 내비게이션 포함)은 폐기.
- **중앙 스캔 액션**: 탭이 아니라 버튼이다. `tabBarButton`을 커스텀해 원형 강조 버튼으로 렌더하고, 탭 상태를 갖지 않는다.
- **알림**: 웹의 헤더 벨 버튼은 `onClick`이 없는 미구현 상태였다. 앱에서는 **홈 헤더 우측 아이콘 + 미읽음 배지** → `notifications` 화면 push로 신규 구현한다.
- **로그아웃**: 웹은 헤더 버튼이었으나 설정 화면 하단으로 이동.
- **랜딩**: 미인증 첫 진입 화면. 로그인 상태에서는 도달할 수 없다(웹은 로그인 후에도 `/`가 열렸다).

### 3. 오버레이 3계층 규칙

| 계층 | 사용 조건 | expo-router 설정 | 적용 대상 |
|---|---|---|---|
| **스택 push** | 콘텐츠가 화면 한 장 이상이고, 뒤로가기로 되돌아가는 것이 자연스러울 때 | 기본 `Stack.Screen` | 문서 상세/편집, 명함 그룹 관리, 알림 목록, 검색 결과 상세, 설정 하위(프로필·비밀번호·앱 정보) |
| **전체화면 모달** | 독립된 선형 태스크. 탭바를 가리는 것이 옳을 때 | `presentation: 'fullScreenModal'`, `gestureEnabled: false`(스캔 진행 중), `animation: 'slide_from_bottom'` | 스캔 플로우 전체, 챗봇 |
| **바텀시트** | 경량 선택·확인·요약. 배경 맥락을 유지해야 할 때 | `@gorhom/bottom-sheet` 컴포넌트 (라우트 아님) | 삭제 확인, 문서 종류 선택(CLS-03), 정렬/필터, 티켓·영수증 요약 상세, 실패 시트(SCF-*), 이미지 소스 선택(카메라/앨범) |

세부 규칙:
- **바텀시트는 라우트로 만들지 않는다.** 화면 로컬 상태로 제어한다. 이유: 시트에 딥링크가 필요한 경우가 없고, 라우트화하면 Android 뒤로가기 처리와 애니메이션이 이중으로 얽힌다. 대신 시트가 열려 있을 때는 `BackHandler`로 시트만 닫는다.
- **문서 상세는 종류에 따라 갈린다.** 필드가 많은 명함·포스터는 push 화면, 짧은 티켓·영수증은 바텀시트 요약 → `자세히`를 누르면 push. 근거: 웹 `StorageDrawer`(420px 고정폭)는 모바일에서 화면을 100% 점유해 "드로어"의 의미가 사라진다.
- **파괴적 확인은 네이티브 `Alert`**가 아니라 자체 바텀시트를 쓴다. 이유: 브랜드 톤 일관성 + 삭제 대상 미리보기(썸네일·제목)를 함께 보여줄 수 있다. 문구는 원본 `삭제하시겠습니까?` / `확인` / `취소`를 계승.
- **챗봇 진입**: 웹의 드래그 가능한 플로팅 패널을 폐기하고, 홈·보관함·검색 탭에 FAB(탭바 위 `bottom: 탭높이+16, right: 16`) → `chat` 모달. 드래그·`clampPosition`·hover 툴팁·TOP 버튼은 전부 삭제.

### 4. 뒤로가기 · 제스처 규약

| 상황 | 동작 |
|---|---|
| 탭 루트에서 Android 뒤로가기 | 홈 탭이 아니면 홈 탭으로, 홈 탭이면 앱 종료 확인 |
| push 화면 | 표준 pop + iOS 스와이프 백 |
| 스캔 모달 진행 중 | 스와이프 다운 **비활성**. 헤더 `닫기` → `스캔을 종료할까요?` 확인 → 초안 저장 후 종료 |
| 스캔 저장 완료 화면 | 뒤로가기 = 탭 루트 복귀. `다른 이미지 스캔`은 카메라로 **replace**(완료 화면이 백스택에 쌓이지 않게) |
| 바텀시트 열림 | 뒤로가기 = 시트만 닫기 |
| 폼 더티 상태 이탈 | `저장하지 않은 변경사항이 있어요` 확인 시트 |

### 5. 딥링크 스킴

| 항목 | 값 |
|---|---|
| 스킴 | `mora://` (`app.json` `scheme: "mora"`) |
| OAuth 콜백 착지 | `mora://auth/callback?token=…&userId=…&email=…&name=…` |
| 처리 위치 | `(auth)/_layout.tsx`에서 `Linking` 파라미터를 흡수 → SecureStore 저장 → `(app)` 으로 replace. 웹의 `dashboard/layout.tsx` 쿼리 흡수 로직과 동일한 자리 |
| 주의 | 현재 백엔드는 `{FRONTEND_URL}` 기준으로 리다이렉트한다. 앱 전용 콜백을 붙이는 방법과 제약은 [[Auth]] · [[ADR-002 Backend Connectivity]] 참조 |
| 향후 | `mora://document/{type}/{id}` (알림 탭 → 문서 열기)를 예약해 둔다. 파일 기반 라우팅이라 경로가 곧 링크가 된다 |

## 결과

### 긍정
1. 라우트 트리가 파일 트리라서 원본 웹 구조와의 대응이 한눈에 보이고, 신규 화면 추가 비용이 파일 1개다.
2. 딥링크가 경로에서 자동 생성되어 OAuth 콜백·알림 탭 이동을 별도 `linking` 설정 없이 처리한다.
3. 인증 게이트가 레이아웃 라우트 2곳으로 수렴한다. 웹의 "레이아웃 한 곳에서만 가드" 패턴을 그대로 계승해 누락 화면이 생기지 않는다.
4. 보관함 4라우트 → 1화면 통합으로 코드 중복(웹은 4개 페이지가 거의 같은 구조를 복제)이 사라지고, 팀이 목업에 그린 IA와 일치한다.
5. 오버레이 3계층 규칙이 문서화되어 "이건 시트인가 화면인가" 논쟁이 줄어든다.

### 부정
1. **탭 슬롯 5개**는 좁은 기기(360dp)에서 라벨이 빡빡하다. 완화: 라벨 11px, 아이콘 24dp, 중앙 액션은 라벨 없음.
2. **보관함 통합의 대가** — 4종의 서로 다른 필드/정렬/필터를 한 화면이 감당해야 한다. 화면 내부 복잡도가 올라간다. 완화: 종류별 카드 렌더러를 컴포넌트로 분리 → [[Component Library]].
3. **expo-router 규약 학습 비용**. 라우트 그룹 `()`, 레이아웃 라우트, `href={null}` 탭 숨김 같은 관용구를 팀이 익혀야 한다.
4. 파일 기반이라 **라우트 이름 변경이 곧 딥링크 URL 변경**이다. 알림 링크를 서버가 저장하고 있으므로(현재 `linkUrl`은 웹 경로 `"/dashboard/storage/posters"`) 앱은 이 값을 그대로 쓰지 않고 `sourceType`으로 매핑해야 한다.
5. 바텀시트를 라우트로 만들지 않기로 해서, 시트 상태는 화면마다 개별 관리된다. 완화: `useBottomSheet` 훅으로 패턴 통일.

## 재검토 트리거

1. 사용자 테스트에서 **중앙 스캔 버튼의 발견율이 낮게** 나오면 → 홈 화면 상단 대형 CTA를 병행하거나 탭 라벨을 부여.
2. 보관함 단일 화면의 필터 조합이 감당 불가로 커지면 → 종류별 하위 화면으로 재분리.
3. **알림 푸시**가 도입되면 → `mora://document/...` 딥링크 경로를 확정하고 서버 `linkUrl` 매핑 규칙을 [[Navigation Map]]에 고정.
4. expo-router가 메이저 breaking change를 내면 → React Navigation 직접 사용으로 내려갈지 판단(하위 계층이 동일하므로 이전 비용은 제한적).
